# Deploy from Local Code

Run `lizard up` to upload and deploy the current directory, whether or not your code is on GitHub. It packages your working tree as a tarball, sends it to the build nodes, and deploys. For the commands each stack needs, see the guides for [React](/framework-guides/react), [Vue](/framework-guides/vue), [Astro](/framework-guides/astro), [SvelteKit](/framework-guides/sveltekit), [Hugo](/framework-guides/hugo), [Docusaurus](/framework-guides/docusaurus), [VitePress](/framework-guides/vitepress), [FastAPI](/framework-guides/fastapi) and [Streamlit](/framework-guides/streamlit).

## Deploy the current directory

```bash
lizard up
```

- Uploads the current directory as a tarball. Inside a git repository it respects `.gitignore`. Outside git, or with `--no-gitignore`, it skips only a fixed list of build and dependency folders (`node_modules`, `.git`, `dist`, `.next`, `build`, `__pycache__`, `.venv`, `venv`, `.cache`, `coverage`, `.turbo`, `.vercel`) plus `.DS_Store`, `*.pyc`, `*.pyo` and `*.log`, so `.env` files are uploaded. Run `git init` or move secrets out first.
- Forces `sourceType=upload`.
- Streams build logs over SSE and prints the live URL when finished.

If the folder isn't linked to a project yet, `up` links it to your account's default project (the oldest project in your personal workspace, `<username>'s Project` for new accounts) and says so. It does not ask, in a terminal or in CI. To deploy to another project, run `lizard init --name <project>` first or pass `--project <name>`. `lizard init --force` relinks a folder.

Without `--service`, `up` deploys to the service linked to the folder. If none is linked, it takes the name from `package.json` or the folder (a terminal asks you to confirm it). When the project already has a service with that name, `up` deploys to it, even a GitHub service, which it switches to `sourceType=upload`. It also sets that service's port as for a new one: `--port`, the local `EXPOSE` line or `3000`. Otherwise it creates the service. Pass `--service <name>` to choose; a name that doesn't exist yet creates that service.

## Common flags

| Flag | Purpose |
|------|---------|
| `-s, --service <name>` | Service to deploy to; a new name creates it |
| `-p, --project <name>` | Deploy to this project instead of the linked or default one |
| `--build-command <cmd>` | Override the build command |
| `--start-command <cmd>` | Override the start command |
| `--pre-deploy-command <cmd>` | Run at the start of every container, before the start command; needs `--start-command` (see [build configuration](/concepts/build-pipeline#build-configuration-reference)) |
| `--port <number>` | Container port (`0` = [worker mode](/deploy/workers)) |
| `--region <code>` | Region for a new service (ignored for existing services) |
| `-d, --detach` | Start the deploy and exit without streaming logs |
| `-c, --ci` | CI-friendly output |
| `--no-gitignore` | Ignore `.gitignore` and use the fixed skip list instead (a built `dist/` or `build/` is still left out) |

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

## Setting build/start commands

Passing `--build-command` or `--start-command` saves it on the service and switches the service to the **synthesized Dockerfile** path, unless `dockerfilePath` is set. On that path, `Procfile` and `package.json` `scripts.start` are **not** read: set the start command explicitly. See [Build Pipeline](/concepts/build-pipeline). For Python apps, [Django, Flask and FastAPI](https://lizard.build/blog/python-app-hosting#build-and-start-commands) each need their own `gunicorn` or `uvicorn` command.

## Re-deploying an upload service

`lizard up` re-uploads and rebuilds. To rebuild the **last** upload with current variables without re-uploading:

```bash
lizard redeploy --service api
```

## Headless / CI

In CI an unlinked folder also deploys to your default project. To deploy to a chosen project, link it first:

```bash
export LIZARD_TOKEN=liz_xxx   # create one with: lizard keys create <name>
lizard init --name my-project
lizard up --ci --service api
```

## When to prefer GitHub instead

Use uploads to test changes or deploy code with no remote. For an app you plan to maintain, use a [GitHub source](/deploy/github) so pushes auto-redeploy and each deploy appears in the history.
