# Build Pipeline

Builds run on Lizard's build nodes — **you don't need Docker locally**. When you deploy, the platform decides how to turn your source into a container image using a fixed decision order, then runs that image in an isolated pod. Not every [container as a service](https://lizard.build/blog/container-as-a-service) builds the image for you; the blog compares the three shapes the category comes in.

## Build decision order

The platform picks exactly one build strategy, in this order:

1. **Repo Dockerfile at `dockerfilePath`** — if `dockerfilePath` is set on the service, that Dockerfile is used unchanged, even when build or start commands are also set. A set `startCommand` still replaces the Dockerfile's `CMD` at run time.
2. **Synthesized Dockerfile** — otherwise, if `buildCommand` and/or `startCommand` are set on the service (or passed via `lizard up --build-command` / `--start-command`), Lizard generates a Dockerfile from those commands. lizardpack is not invoked.
3. **Dockerfile in the source** — otherwise a `Dockerfile` at the root of the build directory is used (see the GitHub exception below).
4. **lizardpack auto-detect** — otherwise the platform runs **lizardpack**, its buildpack/Dockerfile generator.

### lizardpack auto-detect

lizardpack inspects your repo and builds an optimized multi-stage image. Supported stacks, matched in this order:

**Hugo → Go → Node → Python → Rust → Ruby → PHP → Java → static**

See [Framework guides](/framework-guides) for production scripts, adapters, output paths, and ports. Detection uses project files and dependencies; a repository that matches several providers follows this order.

On this path:

- Uploaded source (`lizard up`) always uses a root `Dockerfile` as written.
- GitHub source uses a root `Dockerfile` as written unless it looks incomplete: it has a `COPY` of `build`, `dist`, `out`, `.next` or `public` written without a trailing slash (`COPY dist /usr/share/nginx/html`) and no `RUN` line that starts with `npm`, `yarn`, `pnpm`, `bun`, `pip`, `pip3`, `bundle`, `cargo`, `go build`, `mvn` or `gradle`. lizardpack then generates a replacement.
- With no Dockerfile, lizardpack generates one for you.
- The **start command** is auto-detected: a `Procfile` `web:` line (Python/Ruby) or `package.json` `scripts.start` (Node) is picked up automatically. For the exact line Django, Flask and FastAPI each want, see [Python app hosting](https://lizard.build/blog/python-app-hosting).
- The **port** is inferred from `EXPOSE`, framework defaults, or an explicit `PORT` env.

> **Gotcha:** On GitHub source, a Dockerfile that copies pre-built output (`COPY dist /dest`) and has no package-manager `RUN` step is treated as incomplete and regenerated by lizardpack. Add a real build step, or set `dockerfilePath` to force verbatim use. See [Dockerfile changes don't apply](/deploy/troubleshooting/incomplete-dockerfile).

## What triggers a rebuild

| Action | Rebuilds? |
|--------|-----------|
| `git push` to the tracked branch | ✅ via GitHub webhook |
| `lizard redeploy` / `lizard up` | ✅ explicit |
| Changing `VITE_*` or `NEXT_PUBLIC_*` vars | ✅ rebuilds a running service; see [build-time variables](#build-time-variables) for when the values reach the build |
| `service set` of build fields (`repoUrl`, `branch`, `sourceType`, `buildCommand`, `dockerfilePath`, `rootDirectory`) | ✅ auto-rebuilds a running service; otherwise run `lizard redeploy` |
| `service set` of runtime-only fields (`startCommand`, `preDeployCommand`, `containerPort`, `watchPatterns`) | ❌ run `lizard redeploy` to apply |
| Any other env var / secret change | ❌ applied on a quick restart (no rebuild) |

> **Don't double-build.** After a `service set` that changes a build field on a running service, the rebuild fires automatically — don't chain a `lizard redeploy` after it, or you'll queue a second redundant build. A crashed or never-deployed service does not rebuild on its own; run `lizard redeploy`.

## Build-time variables

Lizard writes `VITE_*` and `NEXT_PUBLIC_*` variables into the Dockerfile as `ENV` lines in two cases:

- GitHub services without `dockerfilePath`: the lizardpack Dockerfile or the repo's root `Dockerfile` gets them.
- Services with `buildCommand` or `startCommand` whose synthesized Dockerfile is a Node build.

Services deployed with `lizard up` and no build or start command get no Lizard variables at build time. No service gets build args other than `COMMIT_SHA`, so an `ARG` in your Dockerfile stays empty. For public values with `lizard up`, commit them in `.env.production` (check that `.gitignore` does not exclude it), write them into your Dockerfile, or, for a Node server app, set both `buildCommand` and `startCommand`.

## Watching a build

Build logs stream during `lizard up`. For any service:

```bash
lizard logs --build            # the most recent build's logs
lizard events                  # deploy history + replica status
```

If a build fails, read `lizard logs --build`, fix the cause (in your repo, or by adjusting `buildCommand` / `startCommand` via `lizard service set`), then `lizard redeploy`.

## Runtime notes

- **No Docker `HEALTHCHECK`.** The runtime doesn't run Docker's healthcheck loop, so `HEALTHCHECK` directives are ignored. Lizard runs a TCP probe against your port instead (skipped in [worker mode](/deploy/workers)).
- **Don't write a Dockerfile unsolicited.** lizardpack auto-detects most stacks — try a deploy first, and only add a Dockerfile (or set `dockerfilePath`) if the auto-build doesn't fit.

## Build configuration reference

| Field | Description |
|-------|-------------|
| `buildCommand` | Command to build your app → selects the **synthesized Dockerfile** path unless `dockerfilePath` is set |
| `startCommand` | Command to start your app at runtime; replaces the image's `CMD` |
| `preDeployCommand` | Runs at the start of every container (each replica, each restart), before `startCommand`; only runs when `startCommand` is set. Make it safe to run many times and at the same time |
| `dockerfilePath` | Path to a repo Dockerfile to use **verbatim**; wins over `buildCommand` / `startCommand` for the image build |
| `rootDirectory` | Subdirectory to build from (monorepos) |
| `watchPatterns` | Only redeploy when matching paths change |
| `containerPort` | TCP port your app listens on (default `3000`; `0` = [worker](/deploy/workers)) |

Set any of these with `lizard service set <svc> --set <field>=<value>`. Clear a field with an empty value, such as `--set buildCommand=`. See [`lizard service`](/cli/service).
