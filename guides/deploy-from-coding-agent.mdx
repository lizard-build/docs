# Deploy from a coding agent

A coding agent can use Lizard Skill and Lizard CLI to deploy the app it has built. The agent reads the installed CLI's guide, checks the target project, runs the build, and inspects the result. This does not require a separate MCP transport.

## Before you start

Have a working application, permission to deploy it, and an account on Lizard. The application must listen on `0.0.0.0` and the configured port. Run its local checks before starting a cloud build.

## Give the agent the current guide

```bash
npm install -g @lizard-build/cli
lizard skills get core --json
lizard --help --json
```

Lizard Skill loads instructions that match the installed CLI. For a specific command, read its schema rather than guessing flags:

```bash
lizard up --help --json
lizard service set --help --json
```

A useful prompt is:

> Deploy this app with Lizard. Read the installed CLI guide, check the linked project and service, run the app's checks, and show the build result and a working URL. Ask before changing an existing production service or deleting data.

## Choose the source

| Source | Command | Effect |
|---|---|---|
| GitHub repository | `lizard add -r your-org/your-app` | Connects a repository and tracked branch. Later pushes can trigger deployment when auto-deploy is enabled. |
| Local directory | `lizard up` | Uploads the current source directory and deploys it. |
| Existing GitHub service | `lizard redeploy --service api` | Rebuilds the selected repository source with current settings. |

`lizard up` changes an existing GitHub service to the upload source path. Use `git push` or `redeploy` when you want to keep that service connected to GitHub.

## Check the target

```bash
lizard login
lizard status --json
lizard ps --json
```

For a new project, run `lizard init --name YOUR_PROJECT_NAME` from the app directory. Confirm the linked project and service before setting secrets or deploying.

## Connect Managed Postgres

Provision the database, then reference its connection string from the consuming service:

```bash
lizard add postgres
lizard secrets set DATABASE_URL='${{postgres.DATABASE_URL}}' --service api
```

Use the database's actual name if it is not `postgres`. Keep the reference quoted so the local shell does not expand it. Make migrations safe to retry, and check [storage and recovery](/platform/storage-and-recovery) before changing data.

## Verify the result

Read build and runtime logs separately, then call the application URL:

```bash
lizard logs --build --service api --json
lizard logs --service api --json
lizard events --json
lizard ps --json
```

`logs --json` returns a log tail and exits. It is not a stream. A successful build is not enough: check the active service, HTTP response, and a database-backed action if the app uses one.

## When deployment fails

Use the exit code and JSON error from the failed command. A compile error, a process that exits, and an unreachable port require different fixes. See [JSON and automation](/cli/json) and [service never healthy](/deploy/troubleshooting/service-never-healthy). `redeploy` is a new build, not a rollback to an older version.

## Limits and cost

An agent can create billable resources through the same CLI as a person. Check [limits](/platform/limits) and [pricing](https://lizard.build/pricing), and scope credentials to the project and services it needs.
