# Dockerfile の変更が反映されていないようです

リポジトリに `Dockerfile` があり、それを編集したにもかかわらず、Lizard が実行するビルドがあなたの記述と一致しません。

<span id="what-this-means" />

## これは何を意味するのか

プラットフォームは、リポジトリの Dockerfile が**不完全**だと判断し、あなたのものをそのまま使う代わりに [lizardpack](/concepts/build-pipeline) で再生成しました。

<span id="why-this-can-happen" />

## なぜこれが起こるのか

このチェックは GitHub ソースのサービスでのみ行われます。アップロード（`lizard up`）では、ルートの `Dockerfile` が常に記述どおりに使われます。

GitHub ソースでは、次の両方に当てはまる場合に、Lizard はルートの Dockerfile を不完全として扱います:

- `build`、`dist`、`out`、`.next`、`public` のいずれかを末尾のスラッシュなしで `COPY` している（例: `COPY dist /usr/share/nginx/html`）。
- `npm`、`yarn`、`pnpm`、`bun`、`pip`、`pip3`、`bundle`、`cargo`、`go build`、`mvn`、`gradle` のいずれかで始まる `RUN` 行がない。

Lizard はそれらのアーティファクトがイメージの外部でビルドされたと見なし、lizardpack が不足しているビルド手順を含む置き換え用 Dockerfile を生成します。

ほかに 2 つの設定でも、リポジトリのルートの Dockerfile は使われません。`dockerfilePath` が設定されている場合、Lizard はそのファイルを記述どおりに使います。設定されていない場合、`buildCommand` または `startCommand` が設定されていると、Lizard はそれらのコマンドから Dockerfile を合成します。

<span id="possible-solutions" />

## 考えられる解決策

<span id="add-a-real-build-step" />

### 実際のビルド手順を追加する

Dockerfile をそのまま使いたい場合は、ビルド済み出力をコピーするのではなく、実際のビルド手順を追加してください。

```dockerfile
RUN npm ci && npm run build
```

<span id="or-force-verbatim-use" />

### またはそのまま使用するよう強制する

`dockerfilePath` を設定してください。イメージのビルドではビルドコマンドと起動コマンドより優先されますが、`startCommand` が設定されていると、実行時には Dockerfile の `CMD` が置き換えられます。そのため、同じ更新で両方をクリアしてください。空の値を渡すとフィールドがクリアされます:

```bash
lizard service set api --set buildCommand= --set startCommand= --set dockerfilePath=Dockerfile
```
