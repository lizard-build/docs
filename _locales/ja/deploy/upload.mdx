# ローカルコードからデプロイ

コードが GitHub にない場合、または変更をすぐに試したい場合は、`lizard up` を使って現在のディレクトリを直接アップロードできます。作業ツリーを tarball としてパッケージ化し、ビルドノードに送信してデプロイします。各スタックに必要なコマンドについては、[React](/framework-guides/react)、[Vue](/framework-guides/vue)、[Astro](/framework-guides/astro)、[SvelteKit](/framework-guides/sveltekit)、[Hugo](/framework-guides/hugo)、[Docusaurus](/framework-guides/docusaurus)、[VitePress](/framework-guides/vitepress)、[FastAPI](/framework-guides/fastapi)、[Streamlit](/framework-guides/streamlit) のガイドを参照してください。

<span id="deploy-the-current-directory" />

## 現在のディレクトリをデプロイ

```bash
lizard up
```

- 現在のディレクトリを tarball としてアップロードします。git リポジトリ内では `.gitignore` を尊重します。git の外、または `--no-gitignore` を付けた場合は、決まったビルド用・依存関係用フォルダー（`node_modules`、`.git`、`dist`、`.next`、`build`、`__pycache__`、`.venv`、`venv`、`.cache`、`coverage`、`.turbo`、`.vercel`）と、`.DS_Store`、`*.pyc`、`*.pyo`、`*.log` だけをスキップするため、`.env` ファイルはアップロードされます。先に `git init` を実行するか、シークレットを移動してください。
- `sourceType=upload` を強制します。
- SSE 経由でビルドログをストリーミングし、完了時にライブ URL を表示します。

フォルダーがまだプロジェクトにリンクされていない場合、`up` はそのフォルダーをアカウントのデフォルトプロジェクト（個人ワークスペースで最も古いプロジェクト。新しいアカウントでは `<username>'s Project`）にリンクし、そのことを表示します。ターミナルでも CI でも確認は求めません。別のプロジェクトにデプロイするには、先に `lizard init --name <project>` を実行するか、`--project <name>` を渡してください。`lizard init --force` でフォルダーをリンクし直せます。

`--service` を指定しない場合、`up` はフォルダーにリンクされたサービスにデプロイします。リンクされたサービスがなければ、`package.json` またはフォルダーから名前を取ります（ターミナルでは確認を求めます）。その名前のサービスがプロジェクトにすでにあれば、`up` はそのサービスにデプロイします。GitHub サービスであってもデプロイし、`sourceType=upload` に切り替えます。また、そのサービスのポートを新しいサービスと同じ方法で設定します: `--port`、ローカルの `EXPOSE` 行、または `3000` です。該当するサービスがなければ作成します。デプロイ先を選ぶには `--service <name>` を渡します。まだ存在しない名前を渡すと、そのサービスが作成されます。

<span id="common-flags" />

## よく使うフラグ

| フラグ | 目的 |
|------|---------|
| `-s, --service <name>` | デプロイ先のサービス。新しい名前ならそのサービスを作成する |
| `-p, --project <name>` | リンク済みまたはデフォルトのプロジェクトではなく、このプロジェクトにデプロイする |
| `--build-command <cmd>` | build コマンドを上書きする |
| `--start-command <cmd>` | start コマンドを上書きする |
| `--pre-deploy-command <cmd>` | すべてのコンテナの起動時に、start コマンドの前に実行する。`--start-command` が必要（[ビルド設定](/concepts/build-pipeline#build-configuration-reference) を参照） |
| `--port <number>` | コンテナポート（`0` = [worker mode](/deploy/workers)） |
| `--region <code>` | 新しいサービスのリージョン（既存のサービスでは無視される） |
| `-d, --detach` | デプロイを開始して、ログをストリーミングせずに終了する |
| `-c, --ci` | CI 向けの出力 |
| `--no-gitignore` | `.gitignore` を無視し、代わりに決まったスキップ一覧を使う（ビルド済みの `dist/` や `build/` は引き続き除外される） |

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

<span id="setting-buildstart-commands" />

## build/start コマンドの設定

`--build-command` または `--start-command` を渡すと、その値がサービスに保存され、`dockerfilePath` が設定されていない限り、サービスは **synthesized Dockerfile** パスに切り替わります。このパスでは、`Procfile` と `package.json` `scripts.start` は読み取られ**ません**。start コマンドを明示的に設定してください。詳しくは [ビルド Pipeline](/concepts/build-pipeline) を参照してください。特に影響を受けやすいのは Python です。[Django, Flask and FastAPI](https://lizard.build/blog/python-app-hosting#build-and-start-commands) では、それぞれ異なる `gunicorn` または `uvicorn` の行が必要です。

<span id="re-deploying-an-upload-service" />

## アップロードサービスを再デプロイする

`lizard up` は再アップロードして再ビルドします。再アップロードせずに、現在の変数で**前回**のアップロードを再ビルドするには:

```bash
lizard redeploy --service api
```

<span id="headless--ci" />

## ヘッドレス / CI

CI でも、リンクされていないフォルダーはデフォルトプロジェクトにデプロイされます。選んだプロジェクトにデプロイするには、先にリンクしてください:

```bash
export LIZARD_TOKEN=liz_xxx   # create one with: lizard keys create <name>
lizard init --name my-project
lizard up --ci --service api
```

<span id="when-to-prefer-github-instead" />

## 代わりに GitHub を使うべき場合

アップロードは、すばやい反復やリモートがない状況に最適です。長期的に運用するものについては、プッシュ時に自動で再デプロイされ、クリーンなデプロイ履歴も得られるため、[GitHub source](/deploy/github) を使うことをおすすめします。
