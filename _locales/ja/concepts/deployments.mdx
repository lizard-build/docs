# デプロイの仕組み

**deployment** とは、サービスの 1 回のビルドとリリースのことです。サービスは Kubernetes の Pod として実行されます。ビルドが成功しただけでは、アプリケーションが起動したことやリクエストを処理できることは証明されません。

<span id="how-a-deploy-happens" />

## デプロイが行われる仕組み

デプロイは、次のいずれかによってトリガーされます:

- 追跡対象ブランチへの **`git push`**（`github`-source サービスの場合）。
- **`lizard redeploy`**：最新のコミット（git）または最後のアップロードから、現在の変数を使って再ビルドします。
- **`lizard up`**：現在のディレクトリをアップロードしてデプロイします。
- ビルドに影響するフィールドを変更する **`service set`**。

```bash
lizard redeploy --service api      # rebuild + redeploy from current source
lizard up                          # upload cwd and deploy
```

<span id="lifecycle" />

## ライフサイクル

1. **ビルド**：プラットフォームがビルドを実行します（[ビルド Pipeline](/concepts/build-pipeline) を参照）。
2. **Pre-deploy**：`preDeployCommand` と `startCommand` の両方が設定されている場合、コンテナは `sh -c "<pre> && exec <start>"` を実行します。プレデプロイコマンドはすべてのコンテナの起動時（各レプリカ、各再起動）に実行されるため、何度実行しても、また同時に実行しても安全なものにしてください。`startCommand` がない場合はスキップされます。
3. **Start**：Lizard は新しい Pod を古い Pod と並べて起動します。[Workers](/deploy/workers) と[ボリューム](/cli/volume)を接続したサービスは先に古い Pod を停止するため、デプロイと再起動のたびに短時間止まります。
4. **Health check**：TCP プローブが 2 秒ごとにアプリのポートを確認し、トラフィックは ready になった Pod にだけ移ります。Lizard は約 30 秒待機し、それまでに新しい Pod が ready にならない場合、デプロイは失敗として扱われます。Workers ではプローブはスキップされます。
5. **Verify**：リリースのステータスを確認し、アプリケーション URL を呼び出します。ポート到達性は完全なアプリケーションヘルスチェックではありません。

<span id="streaming-output" />

## ストリーミング出力

非デタッチの `lizard up`（または `redeploy`）を実行すると、ビルドログがライブでストリーミングされます。`lizard up --json` を使うと、1 行ごとに 1 つの JSON イベントを受け取れます:

```json
{ "event": "log", "line": "..." }
{ "event": "deployed", "status": "...", "url": "https://..." }
```

最後は `deployed`、`failed`、または `deploying` で終了します。`lizard redeploy --json` はログ行を出力しません。すぐに 1 つのオブジェクト（`status: "deploying"`）を返し、`--wait` を付けた場合は最後に `ok` と最終的な `status` を含む 1 つのオブジェクトを返します。`--detach` を使うと、ストリーミングせずにデプロイを開始してすぐに戻れます。

<span id="inspecting-history" />

## 履歴の確認

```bash
lizard events                  # deploy history + per-replica status
lizard events --limit 25       # show more
lizard ps                      # current services, status, and URLs
```

[ダッシュボード](/dashboard) では、各サービスの **概要** タブにデプロイの一覧が表示されます。1 つを開くと、ステータス、ソース、ビルドログ、再起動を確認できます。

<span id="restarts-vs-redeploys" />

## 再起動と再デプロイ

| コマンド | 何をするか |
|---------|--------------|
| `lizard restart --service <svc>` | **現在の** ビルドを再起動：再ビルドなし |
| `lizard redeploy --service <svc>` | 最新のコミット/アップロードから新しく **ビルド** し、その後リリース |

[`lizard restart`](/cli/restart) と [`lizard redeploy`](/cli/redeploy) を参照してください。`restart` はレプリカを再起動するために使います（例: ホットリロードされなかったランタイムシークレットを反映するため）。新しいビルドが必要な場合は `redeploy` を使ってください。

<span id="recovering-from-a-crash" />

## クラッシュからの復旧

直近のクラッシュまたは再起動のログを確認します:

```bash
lizard logs --restart latest       # log tail around the latest restart
lizard logs --restart <id>         # a specific restart
lizard events                      # see replica status
```

<span id="config-changes-no-rebuild" />

## 設定変更（再ビルドなし）

ほとんどの環境変数とシークレットの変更は、再ビルドなしで適用されます。Lizard はサービスの設定を更新して再起動し、これには数秒かかります。ビルド時の値（`VITE_*`、`NEXT_PUBLIC_*`）とビルドフィールドの変更は、稼働中のサービスの再ビルドを強制します：[再ビルドトリガー表](/concepts/build-pipeline#what-triggers-a-rebuild) と [ビルド時の変数](/concepts/build-pipeline#build-time-variables) を参照してください。

<span id="failed-releases-and-recovery" />

## 失敗したリリースと復旧

ビルドの失敗とアプリケーション起動の失敗は別のケースです。ビルドが失敗しても何も変わらず、稼働中のバージョンがそのまま動き続けます。新しい Pod が ready にならない場合、HTTP サービスは以前のバージョンを配信し続け、新しい Pod にはトラフィックが送られません。worker とボリュームを接続したサービスは新しい Pod の起動前に古い Pod を停止するため、ready にならないリリースでは止まったままになります。アクティブなサービス、ビルドログ、ランタイムログを確認してください。`lizard redeploy` は選択したソースを再度ビルドします。以前のビルドを復元するためのコマンドではありません。必要に応じてソースコミットを元に戻し、それをデプロイして結果を確認してください。[既知の問題](/platform/known-issues) を参照してください。
