# シークレットまたは参照がサービスに反映されない

シークレットまたは `${{name.KEY}}` 参照を設定して再デプロイしても、実行中のサービスでは期待した値が確認できないことがあります。

<span id="what-this-means" />

## これは何を意味するのか

設定した値がサービスのマージ後の環境に一度も入っていないか、アプリの起動前にマージ処理で別の値に上書きされたことを意味します。

<span id="why-this-can-happen" />

## なぜ起こるのか

- **参照先のターゲットまたはキーが存在しません。** 存在しない service / addon 名への参照、またはその addon が公開していないキーへの参照は、デプロイを失敗させる代わりに **空文字列** として解決されます。ビルドログには、空の参照ごとに理由付きの警告が出力されます。ビルドなしで再起動によって適用された変数変更では、警告は表示されません。名前を変更したターゲットは存在しないものとして扱われます。参照は現在の名前と照合されます。
- **より高い優先順位のものに上書きされました。** 値は固定順序でマージされます — `addon-issued env < project secrets < project env < app env < app secrets < platform vars` — そのため、project スコープの (`--global`) シークレットは、同じキーを持つ service スコープのシークレットに静かに隠されることがあります。また、プラットフォーム変数 (`PORT`, `LIZARD_SERVICE_NAME`, `LIZARD_PROJECT_ID`, `LIZARD_PUBLIC_DOMAIN`, `LIZARD_PRIVATE_DOMAIN`) は常に優先されます。`PORT` を自分で設定すると、代わりに Lizard がルーティングするポートが変わります。ただし、ポートが `lizard port` で設定されている場合は除きます。
- **ビルド時の値がビルドに渡っていません。** ほとんどの変数変更は再ビルド不要で適用され、サービスはそれらを取り込むために再起動されます。`VITE_*` と `NEXT_PUBLIC_*` の値はビルド済みアセットに埋め込まれ、これらを変更すると稼働中のサービスではすぐに再ビルドが始まります。その時点でクラッシュまたは停止していたサービスはスキップされます。また、独自の `dockerfilePath` を持つサービスや、build/start コマンドなしで `lizard up` でアップロードされたサービスでは、これらの値がビルド時に渡されることはありません。

<span id="possible-solutions" />

## 考えられる解決策

<span id="check-the-build-log-for-empty-references" />

### ビルドログで空の参照を確認する

サービスへのシェルアクセス (`lizard ssh`) は無効になっています。確認すべき場所はビルドログです。空の参照ごとに、`==> Warning: ... is empty` のような行が理由とともに出力されます。

```bash
lizard logs --build --service api
```

次に、このスコープで有効な参照テンプレートを一覧表示し、名前とキーを自分のものと比較してください。キーについては addon の[ドキュメント化された変数](/addons)を確認してください:

```bash
lizard secrets list --service api --ref
```

<span id="check-for-a-scope-collision" />

### スコープの衝突を確認する

両方のスコープのシークレットを一覧し、比較してください。

```bash
lizard secrets list --service api --show
lizard secrets list --global --show
```

**app secrets は project secrets を上書きする** ことに注意してください。同じキーに service スコープの値が存在する場合、`--global` で設定したものよりそちらが優先されます。

<span id="rebuild-after-a-build-time-change" />

### ビルド時の変更後は再ビルドする

変更したキーが `VITE_*` または `NEXT_PUBLIC_*` で、変更時にサービスがクラッシュまたは停止していた場合は、再ビルドを実行してください。

```bash
lizard redeploy --service api
```

[ビルド時と実行時](/variables#build-time-vs-runtime) および [ビルド パイプライン → 再ビルドをトリガーするもの](/concepts/build-pipeline#what-triggers-a-rebuild) も参照してください。
