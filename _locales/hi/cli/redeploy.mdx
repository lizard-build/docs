# lizard redeploy

वर्तमान चर के साथ एक नई बिल्ड (नवीनतम कमिट / अंतिम अपलोड) को ट्रिगर करें।

<span id="usage" />

## उपयोग

```bash
lizard redeploy [nameOrId] [flags]
```

<span id="flags" />

## फ्लैग्स

| फ्लैग | विवरण |
|------|--------------|
| `-s, --service <name>` | सेवा |
| `-p, --project <id>` | प्रोजेक्ट का नाम, स्लग, या आईडी |
| `--detach` | बिल्ड स्वीकार होने के बाद लौटें |
| `--wait` | बिल्ड और डिप्लॉयमेंट की तैयारी के लिए प्रतीक्षा करें; `--json` के साथ काम करता है |
| `--timeout <seconds>` | बिल्ड के बाद तैयारी के लिए प्रतीक्षा बजट; डिफ़ॉल्ट `120` |
| `--json` | स्क्रिप्ट के लिए JSON लौटाएं |

<span id="examples" />

## उदाहरण

<span id="rebuild-and-redeploy-a-service" />

### एक सेवा को फिर से बनाएं और फिर से डिप्लॉय करें

```bash
lizard redeploy --service api
```

<span id="redeploy-without-streaming-logs" />

### लॉग स्ट्रीम किए बिना फिर से डिप्लॉय करें

```bash
lizard redeploy --service api --detach
```

<span id="wait-in-a-script" />

### एक स्क्रिप्ट में प्रतीक्षा करें

```bash
lizard --json redeploy --service api --wait --timeout 120
```

`--wait` के बिना, JSON मोड बिल्ड अनुरोध स्वीकार होने के बाद लौटता है। `--wait` के साथ, CLI उस बिल्ड का अनुसरण करता है और फिर डिप्लॉयमेंट की तैयारी के लिए प्रतीक्षा करता है। JSON परिणाम में `buildId`, `ok`, और `status` शामिल हैं। एक बिल्ड विफलता, विफल तैयारी जांच, या टाइमआउट एक गैर-शून्य निकास कोड लौटाता है।

एक रुकी हुई सेवा आपको इसे [फिर से शुरू](/cli/pause) करने तक फिर से डिप्लॉय करने से इनकार करती है।

टाइमआउट बिल्ड समाप्त होने के बाद तैयारी पर लागू होता है; यह बिल्ड अवधि को सीमित नहीं करता है या डिप्लॉयमेंट को रद्द नहीं करता है। `containerPort=0` वाले वर्कर बिना HTTP जांच के बैकएंड से तैयारी की स्थिति का उपयोग करते हैं। एक सफल कमांड के बाद, यदि आपके वर्कफ़्लो को एप्लिकेशन व्यवहार को सत्यापित करने की आवश्यकता है तो एप्लिकेशन एंडपॉइंट या संग्रहीत डेटा की जांच करें।
