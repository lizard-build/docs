# lizard up

वर्तमान डायरेक्टरी अपलोड करें और उसे तैनात करें।

<span id="usage" />

## उपयोग

```bash
lizard up [path] [flags]
```

`up` आपके वर्किंग ट्री (या `path`) को एक टारबॉल के रूप में पैकेज करता है, इसे बिल्ड नोड्स पर भेजता है, और इसे तैनात करता है। यह लक्ष्य सेवा पर `sourceType=upload` को मजबूर करता है, SSE पर बिल्ड लॉग स्ट्रीम करता है, और समाप्त होने पर लाइव यूआरएल प्रिंट करता है।

यदि फ़ोल्डर किसी प्रोजेक्ट से लिंक नहीं है, तो `up` इसे आपके खाते के डिफ़ॉल्ट प्रोजेक्ट (आपके व्यक्तिगत वर्कस्पेस में सबसे पुराना प्रोजेक्ट) से लिंक करता है और वहां तैनात करता है, टीटीवाई और सीआई दोनों पर। कहीं और तैनात करने के लिए, पहले `lizard init --name <project>` चलाएं या `--project` पास करें।

<span id="which-service-up-deploys-to" />

### `up` किस सेवा में तैनात होता है

1. वह सेवा जिसे आप `--service` के साथ नाम देते हैं। यदि प्रोजेक्ट में उस नाम की कोई सेवा नहीं है, तो `up` उसे बनाता है।
2. फ़ोल्डर से जुड़ी सेवा।
3. अन्यथा, `package.json` में `name` (स्कोप के बिना) या फ़ोल्डर के नाम पर एक सेवा। टीटीवाई पर, `up` नाम पूछता है और इसे प्रदान करता है।

अंतिम मामले में, यदि प्रोजेक्ट में पहले से ही उस नाम की सेवा है, तो `up` उसमें तैनात होता है। हर `up` स्रोत अपलोड करने के लिए अपने लक्ष्य को स्विच करता है, इसलिए गिटहब सेवा पुश पर तैनाती बंद कर देती है। लक्ष्य को स्वयं चुनने के लिए `--service` पास करें।

<span id="flags" />

## फ्लैग्स

| फ्लैग | विवरण |
|------|-------------|
| `-s, --service <name>` | तैनात की जाने वाली सेवा (डिफ़ॉल्ट: लिंक की गई सेवा)। यदि किसी का भी वह नाम नहीं है, तो `up` उसे बनाता है |
| `-p, --project <id>` | प्रोजेक्ट का नाम, स्लग, या आईडी। एक अनलिंक्ड फ़ोल्डर में, `up` फ़ोल्डर को उससे लिंक करता है और यदि उस नाम का कोई प्रोजेक्ट नहीं है तो उसे बनाता है |
| `--build-command <cmd>` | बिल्ड कमांड को ओवरराइड करें |
| `--start-command <cmd>` | स्टार्ट कमांड को ओवरराइड करें |
| `--pre-deploy-command <cmd>` | हर बार कंटेनर शुरू होने पर (हर रेप्लिका, हर रीस्टार्ट) स्टार्ट कमांड से पहले चलाएं। इसके लिए स्टार्ट कमांड की आवश्यकता है; इसे कई बार चलाने के लिए सुरक्षित बनाएं |
| `--port <number>` | कंटेनर पोर्ट (`0` = वर्कर मोड)। नए सर्विस डिफ़ॉल्ट रूप से `3000` पर सेट होते हैं जब तक कि कोई Dockerfile `EXPOSE` इसे सेट न करे |
| `--region <code>` | नई सर्विस के लिए रीजन; मौजूदा सर्विस के लिए अनदेखा किया जाता है |
| `-d, --detach` | डिप्लॉय शुरू करें और लॉग स्ट्रीम किए बिना बाहर निकलें |
| `-c, --ci` | केवल बिल्ड लॉग स्ट्रीम करें और बिल्ड समाप्त होने पर बाहर निकलें |
| `--no-gitignore` | सब कुछ अपलोड करें, `.gitignore` को अनदेखा करें |

## सबकमांड

### `lizard up status <app-id>`

किसी सर्विस की स्थिति, यूआरएल और नवीनतम बिल्ड स्थिति दिखाएं। उस सर्विस आईडी को पास करें जिसे `up --detach` प्रिंट करता है।

<span id="examples" />

## उदाहरण

<span id="deploy-the-current-directory" />

### वर्तमान डायरेक्टरी को डिप्लॉय करें

```bash
lizard up
```

<span id="deploy-to-a-specific-service-with-a-custom-start-command-and-port" />

### कस्टम स्टार्ट कमांड और पोर्ट के साथ किसी विशिष्ट सर्विस पर डिप्लॉय करें

यदि `api` अभी तक मौजूद नहीं है, तो `up` इसे बनाता है।

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

<span id="deploy-headlessly-in-ci" />

### CI में हेडलेस तरीके से डिप्लॉय करें

```bash
export LIZARD_TOKEN=liz_xxx
lizard init --name my-project
lizard up --ci --service api   # creates api on the first run
```

एक असफल बिल्ड या डिप्लॉय कोड `1` के साथ बाहर निकलता है। `--ci` के साथ, एग्जिट कोड केवल बिल्ड को कवर करता है, इसलिए रिलीज़ को पूरा मानने से पहले `lizard ps --json` की जांच करें। `--detach` अपलोड स्वीकार होने के बाद `0` के साथ बाहर निकलता है। [फ्रेमवर्क सेटअप](/framework-guides#prepare-the-project) देखें।
