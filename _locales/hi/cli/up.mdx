# lizard up

मौजूदा डायरेक्टरी अपलोड करें और उसे डिप्लॉय करें।

<span id="usage" />

## उपयोग

```bash
lizard up [path] [flags]
```

`up` आपके वर्किंग ट्री (या `path`) को टारबॉल के रूप में पैकेज करता है, उसे बिल्ड नोड्स पर भेजता है और डिप्लॉय करता है। यह टारगेट सर्विस पर `sourceType=upload` सेट कर देता है, SSE के ज़रिए बिल्ड लॉग स्ट्रीम करता है और पूरा होने पर लाइव URL प्रिंट करता है।

अगर फ़ोल्डर किसी प्रोजेक्ट से लिंक नहीं है, तो `up` उसे आपके अकाउंट के डिफ़ॉल्ट प्रोजेक्ट (आपके पर्सनल वर्कस्पेस का सबसे पुराना प्रोजेक्ट) से लिंक करता है और वहीं डिप्लॉय करता है, TTY पर भी और CI में भी। कहीं और डिप्लॉय करने के लिए पहले `lizard init --name <project>` चलाएँ या `--project` दें।

<span id="which-service-up-deploys-to" />

### `up` किस सर्विस में डिप्लॉय करता है

1. वह सर्विस जिसका नाम आप `--service` में देते हैं। अगर प्रोजेक्ट में उस नाम की कोई सर्विस नहीं है, तो `up` उसे बना देता है।
2. फ़ोल्डर से लिंक की गई सर्विस।
3. वरना `package.json` के `name` (स्कोप के बिना) या फ़ोल्डर के नाम वाली सर्विस। TTY पर `up` नाम पूछता है और यही नाम सुझाव के रूप में देता है।

आखिरी मामले में, अगर प्रोजेक्ट में उस नाम की सर्विस पहले से है, तो `up` उसी में डिप्लॉय करता है। हर `up` अपनी टारगेट सर्विस का सोर्स बदलकर अपलोड कर देता है, इसलिए GitHub से जुड़ी सर्विस push पर डिप्लॉय होना बंद कर देती है। टारगेट खुद चुनने के लिए `--service` दें।

<span id="flags" />

## फ्लैग्स

| फ्लैग | विवरण |
|------|-------------|
| `-s, --service <name>` | वह सर्विस जिसमें डिप्लॉय करना है (डिफ़ॉल्ट: लिंक की गई सर्विस)। अगर उस नाम की कोई सर्विस नहीं है, तो `up` उसे बना देता है |
| `-p, --project <id>` | प्रोजेक्ट का नाम, स्लग या ID। अनलिंक्ड फ़ोल्डर में `up` फ़ोल्डर को उससे लिंक करता है, और उस नाम का कोई प्रोजेक्ट न हो तो उसे बना देता है |
| `--build-command <cmd>` | बिल्ड कमांड ओवरराइड करें |
| `--start-command <cmd>` | स्टार्ट कमांड ओवरराइड करें |
| `--pre-deploy-command <cmd>` | हर बार कंटेनर शुरू होने पर (हर रेप्लिका, हर रीस्टार्ट) स्टार्ट कमांड से पहले चलती है। इसके लिए स्टार्ट कमांड ज़रूरी है; इसे ऐसा बनाएँ कि कई बार चलाना सुरक्षित हो |
| `--port <number>` | कंटेनर पोर्ट (`0` = वर्कर मोड)। नई सर्विस का डिफ़ॉल्ट पोर्ट `3000` होता है, जब तक Dockerfile का `EXPOSE` कुछ और सेट न करे |
| `--region <code>` | नई सर्विस का रीजन; मौजूदा सर्विस के लिए अनदेखा किया जाता है |
| `-d, --detach` | डिप्लॉय शुरू करें और लॉग स्ट्रीम किए बिना बाहर निकलें |
| `-c, --ci` | सिर्फ़ बिल्ड लॉग स्ट्रीम करें और बिल्ड खत्म होने पर बाहर निकलें |
| `--no-gitignore` | `.gitignore` को अनदेखा करके सब कुछ अपलोड करें |

## सबकमांड

### `lizard up status <app-id>`

सर्विस की स्थिति, URL और लेटेस्ट बिल्ड की स्थिति दिखाएँ। वह सर्विस ID दें जो `up --detach` प्रिंट करता है।

## उदाहरण

<span id="deploy-the-current-directory" />

### मौजूदा डायरेक्टरी डिप्लॉय करें

```bash
lizard up
```

<span id="deploy-to-a-specific-service-with-a-custom-start-command-and-port" />

### कस्टम स्टार्ट कमांड और पोर्ट के साथ किसी खास सर्विस में डिप्लॉय करें

अगर `api` अभी मौजूद नहीं है, तो `up` उसे बना देता है।

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

<span id="deploy-headlessly-in-ci" />

### CI में हेडलेस तरीके से डिप्लॉय करें

```bash
export LIZARD_TOKEN=liz_xxx
lizard init --name my-project
lizard up --ci --service api   # creates api on the first run
```

फ़ेल हुआ बिल्ड या डिप्लॉय कोड `1` के साथ बाहर निकलता है। `--ci` के साथ एग्ज़िट कोड सिर्फ़ बिल्ड के बारे में बताता है, इसलिए रिलीज़ को पूरा मानने से पहले `lizard ps --json` जाँचें। अपलोड स्वीकार होते ही `--detach` `0` के साथ बाहर निकलता है। [फ़्रेमवर्क सेटअप](/framework-guides#prepare-the-project) देखें।
