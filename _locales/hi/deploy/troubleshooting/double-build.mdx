# मेरे रीडिप्लॉय ने उस बिल्ड को रद्द कर दिया जो मेरे परिवर्तन ने शुरू किया था

आपने किसी फ़ील्ड को बदलने के लिए `lizard service set` चलाया, फिर `lizard redeploy`। परिनियोजन में अपेक्षा से अधिक समय लगा, और इतिहास में एक रद्द बिल्ड दिखाई दे सकता है।

<span id="what-this-means" />

## इसका क्या मतलब है

`service set` कॉल ने पहले ही अपने आप एक पुनर्निर्माण शुरू कर दिया था। अनुवर्ती `redeploy` ने उस बिल्ड को रद्द कर दिया, जिसका लॉग `--- Build cancelled: a newer deploy was triggered ---` के साथ समाप्त होता है, और उसी बिल्ड को फिर से शुरू से शुरू किया।

<span id="why-this-can-happen" />

## यह क्यों हो सकता है

किसी सेवा पर **बिल्ड-प्रभावित** फ़ील्ड बदलना — `repoUrl`, `branch`, `sourceType`, `buildCommand`, `dockerfilePath`, या `rootDirectory` — तुरंत एक चल रही सेवा का पुनर्निर्माण करता है। क्रैश हुई या कभी तैनात न हुई सेवा अपने आप पुनर्निर्माण नहीं करती है। **रनटाइम-केवल** फ़ील्ड बदलना — `startCommand`, `preDeployCommand`, `containerPort`, `watchPatterns` — **नहीं** स्वचालित रूप से पुनर्निर्माण करता है; यह केवल अगले परिनियोजन पर प्रभावी होता है।

हर `service set` के बाद आँख बंद करके `redeploy` को चेन करना आसान है, लेकिन यह केवल रनटाइम-केवल फ़ील्ड के लिए समझ में आता है।

<span id="possible-solutions" />

## संभावित समाधान

<span id="check-which-kind-of-field-you-changed" />

### जांचें कि आपने किस प्रकार का फ़ील्ड बदला है

[रीबिल्ड शुरू करने वाले बदलावों की तालिका](/concepts/build-pipeline#what-triggers-a-rebuild) देखें। अगर वह बिल्ड फ़ील्ड है और सेवा चल रही थी, तो रीबिल्ड शुरू हो चुका है — आगे कुछ न करें। अगर सेवा क्रैश थी या कभी डिप्लॉय नहीं हुई थी, तो `lizard redeploy` एक बार चलाएँ।

```bash
lizard events   # is a build already running?
```

<span id="only-redeploy-after-runtime-only-changes" />

### केवल रनटाइम-केवल परिवर्तनों के बाद रीडिप्लॉय करें

```bash
lizard service set api --set startCommand="node server.js"
lizard redeploy --service api   # needed here — startCommand doesn't auto-rebuild
```
