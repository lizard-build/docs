# मेरी सेवा डिप्लॉय होती है लेकिन कभी स्वस्थ नहीं होती

बिल्ड सफल होता है और एक नया पॉड शुरू होता है, लेकिन डिप्लॉय को विफल चिह्नित किया जाता है या नया संस्करण कभी भी ट्रैफ़िक प्राप्त नहीं करता है।

<span id="what-this-means" />

## इसका क्या मतलब है

प्लेटफ़ॉर्म की स्वास्थ्य जाँच — आपके ऐप के पोर्ट पर एक TCP प्रोब — कभी पास नहीं होती है, इसलिए ट्रैफ़िक कभी भी नए पॉड में स्थानांतरित नहीं होता है। Lizard लगभग 30 सेकंड तक प्रतीक्षा करता है, फिर डिप्लॉय को विफल चिह्नित करता है। एक सेवा जो पहले से चल रही थी, वह अपने पिछले संस्करण की सेवा जारी रखती है, जब तक कि उसमें संलग्न वॉल्यूम न हो: तब उसका पुराना पॉड पहले रुक जाता है, और सेवा तब तक डाउन रहती है जब तक कि डिप्लॉय पास न हो जाए। पहला डिप्लॉय क्रैश के रूप में दिखाई देता है।

<span id="why-this-can-happen" />

## यह क्यों हो सकता है

- **आपका ऐप अपेक्षित पोर्ट पर नहीं सुन रहा है।** Lizard एक `PORT` पर्यावरण चर (डिफ़ॉल्ट कंटेनर पोर्ट `3000`) इंजेक्ट करता है और जाँचता है कि आपका ऐप वहां पहुंच योग्य है। यदि आपका ऐप किसी भिन्न पोर्ट पर हार्ड-कोडेड है, या कभी भी बाइंड नहीं करता है, तो स्वास्थ्य जाँच कभी पास नहीं होती है। एक Python ऐप सामान्य मामला है: `gunicorn` और `uvicorn` `127.0.0.1` को बाइंड करते हैं जब तक कि आप उन्हें अन्यथा न बताएं, और प्रोब प्रक्रिया के बाहर से आता है। [Python app hosting](https://lizard.build/blog/python-app-hosting#build-and-start-commands) में प्रत्येक फ्रेमवर्क के लिए आवश्यक `--bind 0.0.0.0:$PORT` लाइन होती है।
- **सेवा पोर्ट इमेज से मेल नहीं खाता।** जब `lizard up` बिना `EXPOSE` लाइन वाली Dockerfile से एक सेवा बनाता है, तो यह पोर्ट `3000` सेट करता है, भले ही बेस इमेज कहीं और सुन रही हो, जैसे `nginx` 80. पर। एक `PORT` चर उस पोर्ट को नहीं बदलता है। `lizard port <n>` चलाएं और पुनः डिप्लॉय करें, या एक `EXPOSE` लाइन जोड़ें। देखें [कौन सा पोर्ट Lizard रूट करता है](/deploy/dockerfile#which-port-lizard-routes-to)।
- **सेवा गलती से वर्कर मोड में है।** `containerPort=0` सेट करने से सेवा [वर्कर मोड](/deploy/workers) में चली जाती है, जो **स्वास्थ्य जाँच और लोड-बैलेंसर पंजीकरण को पूरी तरह से छोड़ देता है**। एक सेवा जो HTTP सर्व करने के लिए थी लेकिन `containerPort=0` पर फ्लिप हो गई, वह "सफलतापूर्वक" डिप्लॉय हो जाएगी और कुछ भी सर्व नहीं करेगी — वर्कर मोड अंतर्निहित स्टार्टअप समस्या को सतह पर लाने के बजाय छिपा देता है।

<span id="possible-solutions" />

## संभावित समाधान

<span id="check-the-current-port" />

### वर्तमान पोर्ट की जाँच करें

```bash
lizard port --service api
```

यदि यह `worker mode` प्रिंट करता है, तो सेवा में `containerPort=0` है। यदि यह सेवा HTTP सर्व करने के लिए है तो इसे वापस एक वास्तविक पोर्ट पर सेट करें:

```bash
lizard port 3000 --service api
lizard redeploy --service api
```

<span id="confirm-your-app-is-listening-where-lizard-expects" />

### पुष्टि करें कि आपका ऐप वहां सुन रहा है जहां Lizard अपेक्षा करता है

स्टार्टअप त्रुटियों के लिए रनटाइम लॉग पढ़ें और वह पता जिस पर ऐप सुनता है। इसकी तुलना सेवा पोर्ट से करें, जिसे Lizard ऐप को `PORT` के रूप में पास करता है:

```bash
lizard logs --service api
lizard port --service api
```
