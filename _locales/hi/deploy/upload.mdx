# लोकल कोड से डिप्लॉय करें

मौजूदा डायरेक्टरी को अपलोड और डिप्लॉय करने के लिए `lizard up` चलाएँ, चाहे आपका कोड GitHub पर हो या न हो। यह आपके वर्किंग ट्री को टारबॉल में पैक करता है, उसे बिल्ड नोड्स पर भेजता है और डिप्लॉय करता है। हर स्टैक के लिए ज़रूरी कमांड जानने के लिए [React](/framework-guides/react), [Vue](/framework-guides/vue), [Astro](/framework-guides/astro), [SvelteKit](/framework-guides/sveltekit), [Hugo](/framework-guides/hugo), [Docusaurus](/framework-guides/docusaurus), [VitePress](/framework-guides/vitepress), [FastAPI](/framework-guides/fastapi) और [Streamlit](/framework-guides/streamlit) की गाइड देखें।

<span id="deploy-the-current-directory" />

## मौजूदा डायरेक्टरी डिप्लॉय करें

```bash
lizard up
```

- मौजूदा डायरेक्टरी को टारबॉल के रूप में अपलोड करता है। Git रिपॉज़िटरी के अंदर यह `.gitignore` को मानता है। Git के बाहर, या `--no-gitignore` के साथ, यह बिल्ड और डिपेंडेंसी फ़ोल्डरों की सिर्फ़ एक तय सूची (`node_modules`, `.git`, `dist`, `.next`, `build`, `__pycache__`, `.venv`, `venv`, `.cache`, `coverage`, `.turbo`, `.vercel`) और साथ में `.DS_Store`, `*.pyc`, `*.pyo` और `*.log` को छोड़ता है, इसलिए `.env` फ़ाइलें अपलोड हो जाती हैं। पहले `git init` चलाएँ या सीक्रेट्स को डायरेक्टरी से बाहर ले जाएँ।
- `sourceType=upload` ज़बरदस्ती सेट कर देता है।
- SSE पर बिल्ड लॉग स्ट्रीम करता है और पूरा होने पर लाइव URL प्रिंट करता है।

अगर फ़ोल्डर अभी किसी प्रोजेक्ट से लिंक नहीं है, तो `up` उसे आपके अकाउंट के डिफ़ॉल्ट प्रोजेक्ट से लिंक कर देता है (आपके पर्सनल वर्कस्पेस का सबसे पुराना प्रोजेक्ट; नए अकाउंट में `<username>'s Project`) और यह बात आउटपुट में बताता है। यह न टर्मिनल में पूछता है, न CI में। किसी दूसरे प्रोजेक्ट में डिप्लॉय करने के लिए पहले `lizard init --name <project>` चलाएँ या `--project <name>` पास करें। `lizard init --force` फ़ोल्डर को दोबारा लिंक करता है।

`--service` न देने पर `up` फ़ोल्डर से जुड़ी सर्विस में डिप्लॉय करता है। अगर कोई सर्विस जुड़ी नहीं है, तो वह नाम `package.json` या फ़ोल्डर से लेता है (टर्मिनल में आपसे इसकी पुष्टि माँगी जाती है)। अगर प्रोजेक्ट में उस नाम की सर्विस पहले से है, तो `up` उसी में डिप्लॉय करता है, चाहे वह GitHub सर्विस ही क्यों न हो, और उसे `sourceType=upload` पर स्विच कर देता है। वह उस सर्विस का पोर्ट भी नई सर्विस की तरह सेट करता है: `--port`, लोकल `EXPOSE` लाइन या `3000`। वरना वह नई सर्विस बनाता है। सर्विस ख़ुद चुनने के लिए `--service <name>` पास करें; अगर उस नाम की सर्विस अभी नहीं है, तो वह बन जाती है।

<span id="common-flags" />

## आम फ़्लैग

| फ़्लैग | उद्देश्य |
|------|---------|
| `-s, --service <name>` | किस सर्विस में डिप्लॉय करना है; नया नाम देने पर सर्विस बन जाती है |
| `-p, --project <name>` | लिंक किए गए या डिफ़ॉल्ट प्रोजेक्ट के बजाय इस प्रोजेक्ट में डिप्लॉय करें |
| `--build-command <cmd>` | बिल्ड कमांड को ओवरराइड करें |
| `--start-command <cmd>` | स्टार्ट कमांड को ओवरराइड करें |
| `--pre-deploy-command <cmd>` | हर कंटेनर के शुरू होने पर, स्टार्ट कमांड से पहले चलता है; इसके लिए `--start-command` ज़रूरी है ([बिल्ड कॉन्फ़िगरेशन](/concepts/build-pipeline#build-configuration-reference) देखें) |
| `--port <number>` | कंटेनर पोर्ट (`0` = [वर्कर मोड](/deploy/workers)) |
| `--region <code>` | नई सर्विस का रीजन (मौजूदा सर्विसेज़ के लिए अनदेखा किया जाता है) |
| `-d, --detach` | डिप्लॉय शुरू करें और लॉग स्ट्रीम किए बिना बाहर निकल जाएँ |
| `-c, --ci` | CI के लिए उपयुक्त आउटपुट |
| `--no-gitignore` | `.gitignore` को अनदेखा करें और उसकी जगह तय स्किप लिस्ट इस्तेमाल करें (बिल्ड किया हुआ `dist/` या `build/` तब भी बाहर रहता है) |

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

<span id="setting-buildstart-commands" />

## बिल्ड/स्टार्ट कमांड सेट करना

`--build-command` या `--start-command` पास करने पर वह कमांड सर्विस में सेव हो जाती है और सर्विस **synthesized Dockerfile** वाले पाथ पर चली जाती है, बशर्ते `dockerfilePath` सेट न हो। उस पाथ पर `Procfile` और `package.json` का `scripts.start` **नहीं** पढ़ा जाता: स्टार्ट कमांड साफ़ तौर पर सेट करें। [बिल्ड पाइपलाइन](/concepts/build-pipeline) देखें। Python ऐप्स में [Django, Flask और FastAPI](https://lizard.build/blog/python-app-hosting#build-and-start-commands) तीनों को अपनी-अपनी `gunicorn` या `uvicorn` कमांड चाहिए।

<span id="re-deploying-an-upload-service" />

## अपलोड सर्विस को फिर से डिप्लॉय करना

`lizard up` दोबारा अपलोड और रीबिल्ड करता है। दोबारा अपलोड किए बिना, मौजूदा वेरिएबल्स के साथ **पिछले** अपलोड को रीबिल्ड करने के लिए:

```bash
lizard redeploy --service api
```

<span id="headless--ci" />

## हेडलेस / CI

CI में भी बिना लिंक वाला फ़ोल्डर आपके डिफ़ॉल्ट प्रोजेक्ट में डिप्लॉय होता है। किसी चुने हुए प्रोजेक्ट में डिप्लॉय करने के लिए पहले उसे लिंक करें:

```bash
export LIZARD_TOKEN=liz_xxx   # create one with: lizard keys create <name>
lizard init --name my-project
lizard up --ci --service api
```

<span id="when-to-prefer-github-instead" />

## GitHub कब बेहतर है

बदलाव टेस्ट करने या बिना रिमोट वाला कोड डिप्लॉय करने के लिए अपलोड इस्तेमाल करें। जिस ऐप को आप लंबे समय तक मेंटेन करने वाले हैं, उसके लिए [GitHub सोर्स](/deploy/github) इस्तेमाल करें, ताकि हर पुश पर अपने आप रीडिप्लॉय हो और हर डिप्लॉय हिस्ट्री में दिखे।
