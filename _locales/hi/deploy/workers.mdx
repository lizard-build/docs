# बैकग्राउंड वर्कर्स

Lizard पर एक बैकग्राउंड वर्कर बिना HTTP पोर्ट वाली सर्विस है: एक क्यू कंज्यूमर, अपडेट के लिए पोल करने वाला बॉट, एक रिकंसीलर, या एक पोलिंग लूप। कंटेनर पोर्ट को `0` पर सेट करके इसे **वर्कर मोड** में चलाएं, उदाहरण के लिए `lizard up --port 0` के साथ। वर्कर को कोई `PORT`, कोई रेडीनेस प्रोब और कोई पब्लिक रूट नहीं मिलता है, इसलिए यह HTTP का जवाब न देने के लिए कभी भी अनहेल्दी चिह्नित नहीं होता है। इसे जॉब क्यू के लिए [Managed Redis](/addons/redis) के साथ पेयर करें। चैट बॉट भी वर्कर होते हैं; [टेलीग्राम बॉट](/guides/telegram-bot) और [डिस्कॉर्ड बॉट](/guides/discord-bot) गाइड देखें।

<span id="what-worker-mode-changes" />

## वर्कर मोड क्या बदलता है

जब `containerPort=0`, प्लेटफ़ॉर्म:

- **`PORT` इंजेक्शन को छोड़ देता है**: वर्कर कहीं भी बाइंड नहीं होता है।
- **TCP रेडीनेस प्रोब को छोड़ देता है**: कोई गलत-पॉजिटिव "अनहेल्दी" स्थिति नहीं। नया पॉड शुरू होने से पहले पुराना पॉड बंद हो जाता है।
- सिंथेसाइज्ड डॉकरफ़ाइल में **`EXPOSE` को छोड़ देता है**।
- **लोड-बैलेंसर रूट पंजीकरण को छोड़ देता है**: कुछ भी सर्व नहीं किया जाता है। (एक जेनरेटेड `*.onlizard.com` डोमेन अभी भी सर्विस पर दिखाई दे सकता है, लेकिन यह प्रतिक्रिया नहीं देगा।)

<span id="enable-worker-mode" />

## वर्कर मोड सक्षम करें

तीन समतुल्य तरीके:

```bash
# New upload-source worker
lizard up --port 0

# Flip an existing service
lizard port 0 --service worker

# Via the config:apply path
lizard service set worker --set containerPort=0
```

वर्कर मोड लागू करने के लिए पोर्ट बदलने के बाद रीडिप्लॉय करें।

<span id="check-the-current-port" />

## वर्तमान पोर्ट की जाँच करें

```bash
lizard port --service worker
```

कमांड वर्तमान कंटेनर पोर्ट प्रिंट करता है, या `worker mode` जब यह `0` होता है।

<span id="when-not-to-use-worker-mode" />

## वर्कर मोड का उपयोग कब न करें

नियमित HTTP सर्विस के लिए वर्कर मोड का उपयोग न करें जो शुरू होने में धीमी है। वर्कर मोड पहुंच-योग्यता जांच को पूरी तरह से अक्षम कर देता है, इसलिए यह एक सर्वर का पता नहीं लगाएगा जो सुनने में विफल रहता है। यदि आपकी सर्विस को ट्रैफ़िक सर्व करना है, तो एक वास्तविक पोर्ट रखें और इसके बजाय स्टार्टअप को ठीक करें।

<span id="run-a-queue-consumer" />

## एक क्यू कंज्यूमर चलाएं

[redis-worker उदाहरण](https://github.com/lizard-build/docs/tree/23635ba7e162bafce75d3f6206553b3ef2c0c48e/_examples/redis-worker) का उपयोग करें। यह एक जॉब को पेंडिंग लिस्ट से प्रोसेसिंग लिस्ट में ले जाता है, उसके अपरकेस परिणाम को स्टोर करता है, और Redis ट्रांज़ैक्शन में जॉब को स्वीकार करता है। एक रेप्लिका रखें: स्टार्टअप रिकवरी एक सिंगल कंज्यूमर मानती है। उदाहरण Python 3.13 और redis-py 6.4.0. का उपयोग करता है।

उसके Dockerfile वाले डायरेक्टरी से:

```bash
lizard init --name queue-example
lizard add --service worker
lizard add redis
lizard secrets set REDIS_URL='${{redis.REDIS_URL}}' --service worker
lizard up --service worker --port 0
```

यदि कोई कमांड प्रमाणीकरण की आवश्यकता होने की रिपोर्ट करता है तो `lizard login` के साथ साइन इन करें। यदि यह `redis` नहीं है तो डेटाबेस का वास्तविक नाम उपयोग करें। संदर्भ को उद्धृत रखें। एप्लिकेशन अपलोड करने से पहले इसे सेट करें।

अंतिम डिप्लॉय इवेंट की जांच करें, फिर वर्कर की जांच करें:

```bash
lizard port --service worker
lizard logs --service worker --json
```

अपने कंप्यूटर से एक जॉब सबमिट करें। `lizard run --service redis` Redis एडऑन के कनेक्शन मानों के साथ एक लोकल कमांड चलाता है, जिसमें उसका पब्लिक `REDIS_URL` शामिल है:

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt
lizard run --service redis -- python jobs.py enqueue first-job
lizard run --service redis -- python jobs.py result first-job
```

प्रक्रिया `Queue worker ready` प्रिंट करती है, फिर जॉब चलने के बाद `Processed first-job`। यदि लॉग टेल खाली है, तो जॉब जांच पर भरोसा करें; [टेस्ट परिणाम](/guides/validation) देखे गए लॉगिंग सीमा को रिकॉर्ड करते हैं। परिणाम कमांड 30 सेकंड तक प्रतीक्षा करता है और `{"id": "first-job", "result": "HELLO"}` प्रिंट करता है। एक चलती हुई प्रक्रिया अकेले यह साबित नहीं करती है कि यह एक जॉब का उपभोग कर सकती है।

<span id="verify-a-restart" />

## पुनः आरंभ सत्यापित करें

इस परीक्षण सेवा के लिए, वर्कर को पुनः आरंभ करें और एक और जॉब सबमिट करें:

```bash
lizard restart --service worker
lizard run --service redis -- python jobs.py result first-job
lizard run --service redis -- python jobs.py enqueue after-restart
lizard run --service redis -- python jobs.py result after-restart
```

यदि `after-restart` 30 सेकंड के बाद कोई परिणाम नहीं देता है, तो सेवा के `lizard ps --json` में `running` पर वापस आने की प्रतीक्षा करें और परिणाम कमांड को फिर से चलाएं। दोनों परिणाम `HELLO` होने चाहिए। पहला परिणाम Redis में रहता है, इसलिए वर्कर पुनः आरंभ इसे हटाता नहीं है। स्टार्टअप पर एकल उपभोक्ता अप्रसंस्कृत प्रविष्टि को पेंडिंग सूची में वापस कर देता है।

यह डेमो केवल `jobs.py` द्वारा बनाई गई JSON जॉब्स स्वीकार करता है। यह डेड-लेटर क्यू, अविश्वसनीय उत्पादकों के लिए सत्यापन, या बिल्कुल-एक बार बाहरी साइड इफेक्ट लागू नहीं करता है। भुगतान, ईमेल या अन्य प्रभावों के लिए एक स्थापित क्यू लाइब्रेरी और आइडम्पोटेंट हैंडलर का उपयोग करें। Redis ड्यूरेबिलिटी और बैकअप वर्कर रीस्टार्ट व्यवहार से अलग हैं; [स्टोरेज और रिकवरी](/platform/storage-and-recovery) देखें।

<span id="troubleshooting" />

## समस्या निवारण

| लक्षण | जाँच |
|---|---|
| सेवा अनुपलब्ध | प्रोजेक्ट बनाने के बाद `lizard add --service worker` चलाएं। |
| कोई `Queue worker ready` नहीं | सेवा-स्कोप वाले `REDIS_URL`, एडऑन की तत्परता और कनेक्शन त्रुटियों की जाँच करें। कनेक्शन स्ट्रिंग कभी भी प्रिंट न करें। |
| वर्कर को HTTP पोर्ट की अपेक्षा है | `containerPort=0` सेट करें; चलते हुए सेवा पर इसे बदलने के लिए पुनः परिनियोजन की आवश्यकता होती है। |
| 30 सेकंड के बाद कोई परिणाम नहीं | वर्कर लॉग पढ़ें और जॉब आईडी सत्यापित करें। यह उदाहरण केवल अपने स्वयं के `jobs.py` से जॉब स्वीकार करता है। |
| डुप्लिकेट प्रभाव | पुनः प्रयास से काम फिर से चल सकता है। यह उदाहरण जॉब आईडी द्वारा एक परिणाम संग्रहीत करता है; बाहरी प्रभावों के लिए उनकी अपनी आइडम्पोटेंसी की आवश्यकता होती है। |

## यह भी देखें

- [`lizard port`](/cli/port): सेवा के कंटेनर पोर्ट को दिखाएं या बदलें।
- [सेवा कभी स्वस्थ नहीं होती](/deploy/troubleshooting/service-never-healthy): सबसे आम वर्कर-मोड गलत कॉन्फ़िगरेशन।
- [प्रबंधित एडऑन](/addons): स्टेटफुल वर्कलोड के लिए Redis, Postgres, और S3।
- [Python ऐप होस्टिंग](https://lizard.build/blog/python-app-hosting#django-postgres-and-celery-need-separate-checks): एक Celery वर्कर एक ही इमेज है जिसमें एक अलग कमांड और कोई HTTP पोर्ट नहीं है।

जाँची गई संस्करणों, क्लाउड परिणामों और शेष सीमाओं के लिए [परिदृश्य परीक्षण परिणाम](/guides/validation) देखें।
