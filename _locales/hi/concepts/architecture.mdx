# आर्किटेक्चर

Lizard सेवाओं को परियोजनाओं में और परियोजनाओं को वर्कस्पेस में समूहित करता है। प्रबंधित ऐडऑन एक परियोजना से संबंधित हैं।

```
workspace
└── project
    ├── service (app)          ← built from GitHub or an upload
    ├── service (worker)       ← background job, no HTTP port
    └── addons
        ├── postgres
        ├── redis
        └── s3
```

<span id="workspace" />

## वर्कस्पेस

एक **वर्कस्पेस** खाता या संगठन स्तर है। आप कम से कम एक से संबंधित हैं, और बिलिंग, सदस्य और परियोजनाएं इसके अंतर्गत रहती हैं। उन तक पहुंचें जिन्हें आप एक्सेस कर सकते हैं:

```bash
lizard workspace list
```

कई कमांड `-w, --workspace <ws>` स्वीकार करते हैं ताकि यह स्पष्ट किया जा सके जब एक ही परियोजना का नाम एक से अधिक वर्कस्पेस में मौजूद हो। मालिक कैप कर सकता है कि एक वर्कस्पेस एक बार में कितने सैंडबॉक्स चला सकता है और `lizard workspace limits` के साथ कितना CPU, मेमोरी और डिस्क का उपयोग कर सकता है (देखें [`lizard workspace`](/cli/workspace))।

<span id="project" />

## प्रोजेक्ट

एक **परियोजना** एक वर्कस्पेस के अंदर संबंधित सेवाओं और ऐडऑन को समूहित करती है। आपकी वर्किंग डायरेक्टरी को एक परियोजना से *लिंक* किया जाता है, और वह लिंक (`~/.lizard/config.json` में संग्रहीत) ही वह तरीका है जिससे CLI जानता है कि आप क्या लक्षित कर रहे हैं।

```bash
lizard init --name my-project   # create or select a project, link the cwd
lizard link --project my-project  # link to an existing project
lizard status                   # show the current directory's link
lizard unlink                   # remove the link
lizard project list             # all projects in the workspace
```

एक फ़ोल्डर जिसे आपने लिंक नहीं किया है, वह आपके खाते की **डिफ़ॉल्ट परियोजना** का उपयोग करता है: आपके व्यक्तिगत वर्कस्पेस में सबसे पुरानी परियोजना, एक नए खाते के लिए `<username>'s Project`। `lizard up`, `lizard add`, `lizard sandbox create` और अन्य परियोजना कमांड वहां जाते हैं जब तक कि आप फ़ोल्डर को लिंक नहीं करते या `--project` पास नहीं करते।

> **टिप:** परियोजना के लिए रेपो या निर्देशिका नाम का उपयोग करें, और सेवाओं के लिए ऐप-शैली के नामों (`api`, `worker`, `web`) का उपयोग करें।

<span id="service" />

## सर्विस

एक **सेवा** एक एकल परिनियोजन योग्य इकाई है। इसका स्रोत इनमें से एक है:

- **`github`**: एक कनेक्टेड GitHub रेपो। ट्रैक की गई शाखा पर पुश स्वचालित रूप से पुनः परिनियोजित होते हैं।
- **`upload`**: `lizard up` के साथ अपलोड किया गया एक टारबॉल।

प्रत्येक चल रही सेवा अपनी **अलग पॉड** के रूप में चलती है जिसमें एक डिफ़ॉल्ट-डिनाई नेटवर्क नीति, एक उत्पन्न `<name>-<suffix>.onlizard.com` डोमेन (पुरानी सेवाएं `<words>.<region>.onlizard.com` रखती हैं), और स्वचालित TLS होता है। यह [कंटेनर सेवा के रूप में](https://lizard.build/blog/container-as-a-service) है: आप कंटेनर की आपूर्ति करते हैं और Lizard इसे चलाता है। ब्लॉग बताता है कि कौन से कार्य आपके बने रहते हैं। सेवाओं का निरीक्षण और प्रबंधन करें:

```bash
lizard ps                       # list services with status + URL
lizard service show             # full config as JSON
lizard service set <svc> --set <field>=<value>
lizard service rename <new-name> --service <svc>
lizard service delete --service <svc>
```

किसी सेवा को डिलीट किए बिना रोकने के लिए, [`lizard pause`](/cli/pause) का उपयोग करें; जब उसे कोई ट्रैफ़िक न मिले तो उसे स्लीप मोड में रखने के लिए, [`lizard sleep`](/cli/sleep) का उपयोग करें।

सेवा कॉन्फ़िगरेशन फ़ील्ड **फ्लैट** होते हैं और वायर स्कीमा (जैसे `repoUrl`, `branch`, `buildCommand`, `startCommand`, `containerPort`, `rootDirectory`) पर 1:1 मैप करते हैं। कोई `build.*` / `deploy.*` नेस्टिंग नहीं है। पूरी सूची के लिए [`lizard service`](/cli/service) देखें।

<span id="app-vs-worker-services" />

### ऐप बनाम वर्कर सेवाएं

डिफ़ॉल्ट रूप से एक सेवा एक **HTTP ऐप** होती है जो एक पोर्ट (डिफ़ॉल्ट `3000`) पर सुनती है और उसके डोमेन पर सर्व की जाती है। एक सेवा जो पोर्ट पर नहीं सुनती है, जैसे कि क्यू कंज्यूमर, रिकंसीलर, या पोलिंग लूप, उसे `containerPort=0` सेट करके [**वर्कर मोड**](/deploy/workers) में चलना चाहिए। वर्कर पोर्ट इंजेक्शन, रीचैबिलिटी हेल्थ चेक और लोड-बैलेंसर रजिस्ट्रेशन को छोड़ देते हैं।

<span id="managed-addons" />

## मैनेज्ड एडऑन

**ऐड-ऑन** Managed Postgres, Managed Redis, और Managed Object Storage (S3-संगत) हैं जिन्हें आप प्रति प्रोजेक्ट प्रावधान करते हैं:

```bash
lizard add postgres redis s3
```

प्रत्येक ऐड-ऑन पर्यावरण चर का एक निश्चित सेट एक्सपोज़ करता है जिसे आपकी सेवाएं **संदर्भ** (`${{<addon-name>.KEY}}`) द्वारा उपभोग करती हैं। [प्रबंधित ऐड-ऑन](/addons) देखें।

<span id="cross-resource-references" />

## क्रॉस-रिसोर्स रेफरेंस

किसी अन्य संसाधन के पर्यावरण से सेवा या ऐड-ऑन मान पढ़ने के लिए, इसका उपयोग करें:

```
${{<name>.<KEY>}}
```

संदर्भ **डिप्लॉय समय** पर लक्ष्य के मर्ज किए गए पर्यावरण के विरुद्ध हल होते हैं। वे लक्ष्य के **वर्तमान नाम** से मेल खाते हैं: यदि आप किसी सेवा या ऐड-ऑन का नाम बदलते हैं, तो पुराने नाम का उपयोग करने वाले प्रत्येक संदर्भ को अपडेट करें। एक अनुपलब्ध लक्ष्य या कुंजी का संदर्भ एक खाली स्ट्रिंग में हल होता है (यह डिप्लॉय को **विफल नहीं** करता है); केवल सर्कुलर संदर्भ ही त्रुटि देते हैं।

```bash
# Wire a service to the project's Postgres
lizard secrets set DATABASE_URL='${{postgres.DATABASE_URL}}' --service api
```

जांचें कि संदर्भ हल हो गया है। बिल्ड लॉग हर उस संदर्भ के लिए एक चेतावनी प्रिंट करता है जो एक खाली मान में हल हुआ, और `secrets list` दिखाता है कि क्या संग्रहीत है:

```bash
lizard logs --build --service api
lizard secrets list --service api --show
```

## प्लेटफ़ॉर्म-इंजेक्टेड वेरिएबल्स

Lizard इन चरों को हर सेवा पर सेट करता है; आप उन्हें ओवरराइड नहीं कर सकते:

| वेरिएबल | विवरण |
|----------|-------------|
| `PORT` | वह पोर्ट जिस पर आपके ऐप को सुनना चाहिए (वर्कर मोड में छोड़ा गया) |
| `LIZARD_SERVICE_NAME` | सेवा का नाम |
| `LIZARD_PROJECT_ID` | प्रोजेक्ट आईडी |
| `LIZARD_PUBLIC_DOMAIN` | सेवा का सार्वजनिक डोमेन (डोमेन असाइन होने के बाद एक बार सेट किया गया) |
| `LIZARD_PRIVATE_DOMAIN` | सेवा का निजी होस्टनाम, `<host>.lizard.internal`, उसी प्रोजेक्ट से पहुंच योग्य |

यह देखने के लिए कि ये आपके अपने चर और पूर्ण प्राथमिकता क्रम के साथ कैसे इंटरैक्ट करते हैं, [चर और रहस्य](/variables) देखें।
