# आर्किटेक्चर

Lizard सर्विसेज़ को प्रोजेक्ट्स में और प्रोजेक्ट्स को वर्कस्पेस में ग्रुप करता है। मैनेज्ड ऐडऑन किसी प्रोजेक्ट के होते हैं।

```
workspace
└── project
    ├── service (app)          ← built from GitHub or an upload
    ├── service (worker)       ← background job, no HTTP port
    └── addons
        ├── postgres
        ├── redis
        └── s3
```

<span id="workspace" />

## वर्कस्पेस

**वर्कस्पेस** अकाउंट या संगठन का स्तर है। आप कम से कम एक वर्कस्पेस के सदस्य होते हैं, और बिलिंग, सदस्य और प्रोजेक्ट्स उसी के अंदर होते हैं। जिन वर्कस्पेस तक आपकी पहुँच है, उनकी लिस्ट देखें:

```bash
lizard workspace list
```

जब एक ही नाम का प्रोजेक्ट एक से ज़्यादा वर्कस्पेस में हो, तो स्पष्ट करने के लिए कई कमांड `-w, --workspace <ws>` लेती हैं। मालिक `lizard workspace limits` से यह सीमित कर सकता है कि वर्कस्पेस एक साथ कितने सैंडबॉक्स चलाए और कितना CPU, मेमोरी और डिस्क इस्तेमाल करे (देखें [`lizard workspace`](/cli/workspace))।

<span id="project" />

## प्रोजेक्ट

**प्रोजेक्ट** किसी वर्कस्पेस के अंदर आपस में जुड़ी सर्विसेज़ और ऐडऑन को एक साथ रखता है। आपकी वर्किंग डायरेक्टरी किसी प्रोजेक्ट से *लिंक* की जाती है, और इसी लिंक (`~/.lizard/config.json` में सेव) से CLI जानता है कि आप किसे टारगेट कर रहे हैं।

```bash
lizard init --name my-project   # create or select a project, link the cwd
lizard link --project my-project  # link to an existing project
lizard status                   # show the current directory's link
lizard unlink                   # remove the link
lizard project list             # all projects in the workspace
```

जिस फ़ोल्डर को आपने लिंक नहीं किया है, वह आपके अकाउंट के **डिफ़ॉल्ट प्रोजेक्ट** का उपयोग करता है: आपके पर्सनल वर्कस्पेस का सबसे पुराना प्रोजेक्ट, जो नए अकाउंट के लिए `<username>'s Project` होता है। `lizard up`, `lizard add`, `lizard sandbox create` और प्रोजेक्ट से जुड़ी दूसरी कमांड वहीं जाती हैं, जब तक आप फ़ोल्डर को लिंक न करें या `--project` न दें।

> **टिप:** प्रोजेक्ट के लिए रिपॉज़िटरी या डायरेक्टरी का नाम रखें, और सर्विसेज़ के लिए ऐप जैसे नाम (`api`, `worker`, `web`)।

<span id="service" />

## सर्विस

**सर्विस** डिप्लॉय की जा सकने वाली एक अलग यूनिट है। इसका सोर्स इनमें से एक होता है:

- **`github`**: कनेक्ट की गई GitHub रिपॉज़िटरी। ट्रैक की गई ब्रांच पर push होते ही सर्विस अपने-आप रीडिप्लॉय होती है।
- **`upload`**: `lizard up` से अपलोड किया गया टारबॉल।

हर चल रही सर्विस अपने **अलग (isolated) पॉड** में चलती है, जिसमें डिफ़ॉल्ट-डिनाई नेटवर्क पॉलिसी, जेनरेटेड `<name>-<suffix>.onlizard.com` डोमेन (पुरानी सर्विसेज़ के पास `<words>.<region>.onlizard.com` बना रहता है) और ऑटोमैटिक TLS होता है। यही [container as a service](https://lizard.build/blog/container-as-a-service) है: कंटेनर आप देते हैं और Lizard उसे चलाता है। ब्लॉग बताता है कि कौन-से काम आपकी ज़िम्मेदारी बने रहते हैं। सर्विसेज़ को देखने और मैनेज करने के लिए:

```bash
lizard ps                       # list services with status + URL
lizard service show             # full config as JSON
lizard service set <svc> --set <field>=<value>
lizard service rename <new-name> --service <svc>
lizard service delete --service <svc>
```

सर्विस को डिलीट किए बिना रोकने के लिए [`lizard pause`](/cli/pause) का उपयोग करें; ट्रैफ़िक न मिलने पर उसे स्लीप करने देने के लिए [`lizard sleep`](/cli/sleep) का।

सर्विस कॉन्फ़िगरेशन के फ़ील्ड **फ़्लैट** हैं और वायर स्कीमा से 1:1 मैप होते हैं (जैसे `repoUrl`, `branch`, `buildCommand`, `startCommand`, `containerPort`, `rootDirectory`)। इनमें कोई `build.*` / `deploy.*` नेस्टिंग नहीं है। पूरी लिस्ट के लिए [`lizard service`](/cli/service) देखें।

<span id="app-vs-worker-services" />

### ऐप बनाम वर्कर सर्विसेज़

डिफ़ॉल्ट रूप से सर्विस एक **HTTP ऐप** होती है, जो किसी पोर्ट (डिफ़ॉल्ट `3000`) पर सुनती है और अपने डोमेन पर सर्व होती है। जो सर्विस किसी पोर्ट पर नहीं सुनती, जैसे क्यू कंज़्यूमर, रिकंसाइलर या पोलिंग लूप, उसे `containerPort=0` सेट करके [**वर्कर मोड**](/deploy/workers) में चलाना चाहिए। वर्कर्स के लिए पोर्ट इंजेक्शन, रीचेबिलिटी हेल्थ चेक और लोड-बैलेंसर रजिस्ट्रेशन नहीं होते।

<span id="managed-addons" />

## मैनेज्ड ऐडऑन

**ऐडऑन** हैं Managed Postgres, Managed Redis और Managed Object Storage (S3-कम्पैटिबल), जिन्हें आप हर प्रोजेक्ट में अलग से बनाते हैं:

```bash
lizard add postgres redis s3
```

हर ऐडऑन एनवायरनमेंट वेरिएबल्स का एक तय सेट देता है, जिसे आपकी सर्विसेज़ **रेफ़रेंस** (`${{<addon-name>.KEY}}`) से इस्तेमाल करती हैं। [मैनेज्ड ऐडऑन](/addons) देखें।

<span id="cross-resource-references" />

## क्रॉस-रिसोर्स रेफ़रेंस

किसी दूसरे रिसोर्स के एनवायरनमेंट से सर्विस या ऐडऑन की वैल्यू पढ़ने के लिए इसका उपयोग करें:

```
${{<name>.<KEY>}}
```

रेफ़रेंस **डिप्लॉय के समय** टारगेट के मर्ज किए गए एनवायरनमेंट से रिज़ॉल्व होते हैं। ये टारगेट के **मौजूदा नाम** से मेल खाते हैं: अगर आप किसी सर्विस या ऐडऑन का नाम बदलते हैं, तो पुराने नाम वाले हर रेफ़रेंस को अपडेट करें। जो टारगेट या की मौजूद नहीं है, उसका रेफ़रेंस खाली स्ट्रिंग में रिज़ॉल्व होता है (इससे डिप्लॉय फ़ेल **नहीं** होता); एरर सिर्फ़ सर्कुलर रेफ़रेंस पर आता है।

```bash
# Wire a service to the project's Postgres
lizard secrets set DATABASE_URL='${{postgres.DATABASE_URL}}' --service api
```

जाँचें कि रेफ़रेंस रिज़ॉल्व हुआ या नहीं। बिल्ड लॉग हर उस रेफ़रेंस पर चेतावनी प्रिंट करता है जो खाली वैल्यू में रिज़ॉल्व हुआ, और `secrets list` दिखाता है कि क्या सेव है:

```bash
lizard logs --build --service api
lizard secrets list --service api --show
```

## प्लेटफ़ॉर्म द्वारा इंजेक्ट किए गए वेरिएबल्स

Lizard ये वेरिएबल्स हर सर्विस पर सेट करता है; आप इन्हें ओवरराइड नहीं कर सकते:

| वेरिएबल | विवरण |
|----------|-------------|
| `PORT` | वह पोर्ट जिस पर आपके ऐप को सुनना चाहिए (वर्कर मोड में सेट नहीं होता) |
| `LIZARD_SERVICE_NAME` | सर्विस का नाम |
| `LIZARD_PROJECT_ID` | प्रोजेक्ट ID |
| `LIZARD_PUBLIC_DOMAIN` | सर्विस का पब्लिक डोमेन (डोमेन असाइन होते ही सेट होता है) |
| `LIZARD_PRIVATE_DOMAIN` | सर्विस का प्राइवेट होस्टनेम, `<host>.lizard.internal`, जिस तक उसी प्रोजेक्ट से पहुँचा जा सकता है |

ये आपके अपने वेरिएबल्स के साथ कैसे काम करते हैं और पूरा प्राथमिकता क्रम क्या है, यह [वेरिएबल्स और सीक्रेट्स](/variables) में देखें।
