# बिल्ड पाइपलाइन

Lizard अपने बिल्ड नोड्स पर आपके स्रोत से एक कंटेनर इमेज बनाता है, फिर इमेज को एक अलग पॉड में चलाता है। आपको स्थानीय रूप से डॉकर की आवश्यकता नहीं है। नीचे दिए गए नियम निर्धारित करते हैं कि Lizard इमेज कैसे बनाता है। इमेज बनाने वाले होस्ट और इमेज की आवश्यकता वाले होस्ट की तुलना के लिए, [सेवा के रूप में कंटेनर](https://lizard.build/blog/container-as-a-service) देखें।

<span id="build-decision-order" />

## बिल्ड निर्णय क्रम

प्लेटफ़ॉर्म इस क्रम में ठीक एक बिल्ड रणनीति चुनता है:

1. **`dockerfilePath` पर रेपो डॉकरफ़ाइल**: यदि सेवा पर `dockerfilePath` सेट है, तो वह डॉकरफ़ाइल अपरिवर्तित उपयोग की जाती है, भले ही बिल्ड या स्टार्ट कमांड भी सेट हों। एक सेट `startCommand` रन टाइम पर डॉकरफ़ाइल के `ENTRYPOINT` और `CMD` को बदल देता है। [डॉकरफ़ाइल के साथ डिप्लॉय](/deploy/dockerfile) देखें।
2. **संश्लेषित डॉकरफ़ाइल**: अन्यथा, यदि सेवा पर `buildCommand` और/या `startCommand` सेट हैं (या `lizard up --build-command` / `--start-command` के माध्यम से पास किए गए हैं), तो Lizard उन कमांड से एक डॉकरफ़ाइल उत्पन्न करता है। lizardpack को कॉल नहीं किया जाता है।
3. **स्रोत में डॉकरफ़ाइल**: अन्यथा बिल्ड डायरेक्टरी के रूट में एक `Dockerfile` का उपयोग किया जाता है (नीचे GitHub अपवाद देखें)।
4. **lizardpack ऑटो-डिटेक्ट**: अन्यथा प्लेटफ़ॉर्म **lizardpack**, इसके बिल्डपैक/डॉकरफ़ाइल जनरेटर को चलाता है।

<span id="lizardpack-auto-detect" />

### lizardpack ऑटो-डिटेक्ट

lizardpack आपके रेपो का निरीक्षण करता है और एक मल्टी-स्टेज इमेज बनाता है। समर्थित स्टैक, इस क्रम में मिलान किए गए:

**Hugo → Go → Node → Python → Rust → Ruby → PHP → Java → static**

उत्पादन स्क्रिप्ट, एडेप्टर, आउटपुट पथ और पोर्ट के लिए [फ़्रेमवर्क गाइड](/framework-guides) देखें: [Hugo](/framework-guides/hugo), [Go](/framework-guides/go), Node ([Node.js](/framework-guides/nodejs), [Next.js](/framework-guides/nextjs), [Nuxt](/framework-guides/nuxt), [SvelteKit](/framework-guides/sveltekit), [Astro](/framework-guides/astro), [React](/framework-guides/react), [Vue](/framework-guides/vue), [Docusaurus](/framework-guides/docusaurus), [VitePress](/framework-guides/vitepress)), Python ([Django](/framework-guides/django), [FastAPI](/framework-guides/fastapi), [Streamlit](/framework-guides/streamlit)) और Ruby ([Rails](/framework-guides/rails))। डिटेक्शन प्रोजेक्ट फ़ाइलों और निर्भरताओं का उपयोग करता है; कई प्रदाताओं से मेल खाने वाला एक रिपॉजिटरी इस क्रम का अनुसरण करता है। Node.js या Python संस्करण को पिन करने के लिए, [रनटाइम संस्करण](/deploy/runtime-versions) देखें।

इस पथ पर:

- अपलोड किया गया स्रोत (`lizard up`) हमेशा एक रूट `Dockerfile` का उपयोग करता है जैसा लिखा गया है।
- GitHub स्रोत एक रूट `Dockerfile` का उपयोग करता है जैसा लिखा गया है जब तक कि यह अधूरा न लगे: इसमें `COPY` `build`, `dist`, `out`, `.next` या `public` बिना अंतिम स्लैश (`COPY dist /usr/share/nginx/html`) के लिखा गया है और कोई `RUN` लाइन नहीं है जो `npm`, `yarn`, `pnpm`, `bun`, `pip`, `pip3`, `bundle`, `cargo`, `go build`, `mvn` या `gradle` से शुरू होती है। lizardpack तब एक प्रतिस्थापन उत्पन्न करता है।
- कोई डॉकरफ़ाइल नहीं होने पर, lizardpack आपके लिए एक उत्पन्न करता है।
- **स्टार्ट कमांड** का स्वतः पता लगाया जाता है: एक `Procfile` `web:` लाइन (Python/Ruby) या `package.json` `scripts.start` (Node) स्वचालित रूप से उठाया जाता है। Django, Flask और FastAPI स्टार्ट कमांड के लिए, [Python ऐप होस्टिंग](https://lizard.build/blog/python-app-hosting) देखें।
- **पोर्ट** `EXPOSE`, फ़्रेमवर्क डिफ़ॉल्ट, या एक स्पष्ट `PORT` env से अनुमान लगाया जाता है।

> **ध्यान दें:** GitHub स्रोत पर, एक डॉकरफ़ाइल जो प्री-बिल्ट आउटपुट (`COPY dist /dest`) कॉपी करती है और जिसमें कोई पैकेज-मैनेजर `RUN` स्टेप नहीं है, उसे अधूरा माना जाता है और lizardpack द्वारा पुनर्जीवित किया जाता है। एक वास्तविक बिल्ड स्टेप जोड़ें, या वर्बेटिम उपयोग को बाध्य करने के लिए `dockerfilePath` सेट करें। [Dockerfile परिवर्तन लागू नहीं होते](/deploy/troubleshooting/incomplete-dockerfile) देखें।

## पुनर्निर्माण को क्या ट्रिगर करता है

| क्रिया | पुनर्निर्माण? |
|--------|-----------|
| `git push` ट्रैक की गई ब्रांच में | ✅ GitHub वेबहुक के माध्यम से ✅ |
| `lizard redeploy` / `lizard up` | ✅ स्पष्ट |
| `VITE_*` या `NEXT_PUBLIC_*` चर बदलना | ✅ एक चल रही सेवा को फिर से बनाता है; बिल्ड पर मान पहुंचने पर [बिल्ड-टाइम चर](#build-time-variables) देखें |
| बिल्ड फ़ील्ड्स (`repoUrl`, `branch`, `sourceType`, `buildCommand`, `dockerfilePath`, `rootDirectory`) का `service set` | ✅ एक चल रही सेवा को स्वचालित रूप से फिर से बनाता है; अन्यथा `lizard redeploy` चलाएँ |
| केवल रनटाइम फ़ील्ड्स (`startCommand`, `preDeployCommand`, `containerPort`, `watchPatterns`) का `service set` | ❌ लागू करने के लिए `lizard redeploy` चलाएँ |
| कोई अन्य env var / सीक्रेट परिवर्तन | ❌ एक त्वरित पुनरारंभ पर लागू (कोई पुनर्निर्माण नहीं) |

> **दो बार बिल्ड न करें।** चल रही सेवा पर बिल्ड फ़ील्ड बदलने वाले `service set` के बाद, Lizard एक पुनर्निर्माण शुरू करता है। उसके बाद `lizard redeploy` चलाने से वह बिल्ड रद्द हो जाता है और फिर से शुरू हो जाता है ([क्यों](/deploy/troubleshooting/double-build))। क्रैश हुई या कभी तैनात न हुई सेवा अपने आप दोबारा नहीं बनती; `lizard redeploy` चलाएँ।

<span id="build-time-variables" />

## बिल्ड-टाइम चर

Lizard दो मामलों में Dockerfile में `VITE_*` और `NEXT_PUBLIC_*` चर को `ENV` लाइनों के रूप में लिखता है:

- `dockerfilePath` के बिना GitHub सेवाएँ: lizardpack Dockerfile या रेपो का रूट `Dockerfile` उन्हें प्राप्त करता है।
- `buildCommand` या `startCommand` वाली सेवाएँ जिनका संश्लेषित Dockerfile एक Node बिल्ड है।

`lizard up` के साथ तैनात की गई सेवाएँ और कोई बिल्ड या स्टार्ट कमांड नहीं होने पर बिल्ड समय पर कोई Lizard चर नहीं मिलता है। बिल्ड आर्गुमेंट्स के अलावा कोई भी सेवा `COMMIT_SHA` प्राप्त नहीं करती है, इसलिए आपके Dockerfile में एक `ARG` खाली रहता है। `lizard up` के साथ सार्वजनिक मानों के लिए, उन्हें `.env.production` में कमिट करें (जांचें कि `.gitignore` इसे बाहर नहीं करता है), उन्हें अपने Dockerfile में लिखें, या, Node सर्वर ऐप के लिए, `buildCommand` और `startCommand` दोनों सेट करें।

<span id="watching-a-build" />

## बिल्ड देखना

`lizard up` के दौरान बिल्ड लॉग स्ट्रीम होते हैं। किसी भी सेवा के लिए:

```bash
lizard logs --build            # the most recent build's logs
lizard events                  # deploy history + replica status
```

यदि बिल्ड विफल हो जाता है, तो `lizard logs --build` पढ़ें, कारण ठीक करें (आपके रेपो में, या `lizard service set` के माध्यम से `buildCommand` / `startCommand` को समायोजित करके), फिर `lizard redeploy` चलाएँ।

<span id="runtime-notes" />

## रनटाइम नोट्स

- **कोई Docker `HEALTHCHECK` नहीं।** रनटाइम Docker के healthcheck लूप को नहीं चलाता है, इसलिए `HEALTHCHECK` निर्देशकों को अनदेखा किया जाता है। Lizard इसके बजाय आपके पोर्ट के विरुद्ध एक TCP प्रोब चलाता है ( [वर्कर मोड](/deploy/workers) में छोड़ा गया)।
- **अनचाहे रूप से Dockerfile न लिखें।** lizardpack अधिकांश स्टैक का स्वतः पता लगाता है: पहले एक डिप्लॉय का प्रयास करें, और केवल तभी Dockerfile जोड़ें (या `dockerfilePath` सेट करें) यदि ऑटो-बिल्ड फिट नहीं होता है।

<span id="build-configuration-reference" />

## बिल्ड कॉन्फ़िगरेशन संदर्भ

| फ़ील्ड | विवरण |
|-------|-------------|
| `buildCommand` | आपके ऐप को बिल्ड करने के लिए कमांड → **संश्लेषित Dockerfile** पथ का चयन करता है जब तक कि `dockerfilePath` सेट न हो |
| `startCommand` | रनटाइम पर आपके ऐप को शुरू करने के लिए कमांड; इमेज के `ENTRYPOINT` और `CMD` को बदल देता है |
| `preDeployCommand` | `startCommand` से पहले, हर कंटेनर (प्रत्येक प्रतिकृति, प्रत्येक पुनरारंभ) की शुरुआत में चलता है; केवल तब चलता है जब `startCommand` सेट हो। इसे कई बार और एक साथ चलाने के लिए सुरक्षित बनाएँ |
| `dockerfilePath` | रिपॉजिटरी Dockerfile का पथ जिसे **यथावत** उपयोग करना है; इमेज बिल्ड के लिए `buildCommand` / `startCommand` पर जीत |
| `rootDirectory` | से बिल्ड करने के लिए सबडायरेक्टरी (मोनोरेपोस) |
| `watchPatterns` | केवल मिलान पथ बदलने पर पुनः तैनात करें |
| `containerPort` | आपका ऐप जिस TCP पोर्ट पर सुनता है (डिफ़ॉल्ट `3000`; `0` = [वर्कर](/deploy/workers)) |

इनमें से किसी को भी `lizard service set <svc> --set <field>=<value>` के साथ सेट करें। एक खाली मान के साथ एक फ़ील्ड साफ़ करें, जैसे `--set buildCommand=`। [`lizard service`](/cli/service) देखें।
