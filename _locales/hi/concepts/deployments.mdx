# डिप्लॉयमेंट्स

**डिप्लॉयमेंट** किसी सर्विस का एक बिल्ड-और-रिलीज़ है। सर्विसेज़ Kubernetes पॉड्स के रूप में चलती हैं। बिल्ड सफल होना अपने-आप में यह साबित नहीं करता कि ऐप्लिकेशन शुरू हो गया है या रिक्वेस्ट्स सर्व कर सकता है।

<span id="how-a-deploy-happens" />

## डिप्लॉय कैसे होता है

ये कार्रवाइयाँ डिप्लॉयमेंट शुरू करती हैं:

- ट्रैक की गई ब्रांच पर **`git push`** (`github` सोर्स वाली सर्विसेज़ के लिए)।
- **`lizard redeploy`**: लेटेस्ट कमिट (git) या आखिरी अपलोड से, मौजूदा वेरिएबल्स के साथ रीबिल्ड।
- **`lizard up`**: मौजूदा डायरेक्टरी अपलोड करना और उसे डिप्लॉय करना।
- ऐसा **`service set`** जो बिल्ड पर असर डालने वाला कोई फ़ील्ड बदलता है।

```bash
lizard redeploy --service api      # rebuild + redeploy from current source
lizard up                          # upload cwd and deploy
```

<span id="lifecycle" />

## लाइफसाइकिल

1. **बिल्ड**: प्लेटफ़ॉर्म आपका बिल्ड चलाता है ([बिल्ड पाइपलाइन](/concepts/build-pipeline) देखें)।
2. **प्री-डिप्लॉय**: अगर `preDeployCommand` और `startCommand` दोनों सेट हैं, तो कंटेनर `sh -c "<pre> && exec <start>"` चलाता है। प्री-डिप्लॉय कमांड हर कंटेनर की शुरुआत में (हर रेप्लिका, हर रीस्टार्ट) चलती है, इसलिए इसे ऐसा बनाएँ कि कई बार और एक साथ चलाना सुरक्षित हो। `startCommand` के बिना यह स्टेप छोड़ दिया जाता है।
3. **स्टार्ट**: Lizard नए पॉड को पुराने पॉड के साथ-साथ शुरू करता है। [वर्कर्स](/deploy/workers) और अटैच [वॉल्यूम](/cli/volume) वाली सर्विसेज़ पहले पुराना पॉड बंद करती हैं, इसलिए हर डिप्लॉय और रीस्टार्ट पर वे थोड़ी देर के लिए डाउन रहती हैं।
4. **हेल्थ चेक**: TCP प्रोब हर 2 सेकंड में ऐप का पोर्ट जाँचता है, और ट्रैफ़िक सिर्फ़ रेडी पॉड पर जाता है। Lizard इसके लिए लगभग 30 सेकंड इंतज़ार करता है; अगर तब तक नया पॉड रेडी नहीं होता, तो डिप्लॉय फ़ेल मार्क कर दिया जाता है। वर्कर्स पर प्रोब नहीं चलता।
5. **जाँच**: रिलीज़ की स्थिति देखें और ऐप्लिकेशन का URL कॉल करें। पोर्ट तक पहुँच पाना ऐप्लिकेशन का पूरा हेल्थ चेक नहीं है।

<span id="streaming-output" />

## आउटपुट स्ट्रीमिंग

जब आप `lizard up` (या `redeploy`) को detach किए बिना चलाते हैं, तो बिल्ड लॉग लाइव स्ट्रीम होते हैं। `lizard up --json` के साथ आपको हर लाइन में एक JSON इवेंट मिलता है:

```json
{ "event": "log", "line": "..." }
{ "event": "deployed", "status": "...", "url": "https://..." }
```

आखिरी इवेंट `deployed`, `failed` या `deploying` होता है। `lizard redeploy --json` कोई लॉग लाइन प्रिंट नहीं करता: यह तुरंत एक ऑब्जेक्ट (`status: "deploying"`) लौटाता है, या `--wait` के साथ आखिर में `ok` और फ़ाइनल `status` वाला एक ऑब्जेक्ट। डिप्लॉय शुरू करके स्ट्रीमिंग के बिना तुरंत लौटने के लिए `--detach` का उपयोग करें।

<span id="inspecting-history" />

## हिस्ट्री देखना

```bash
lizard events                  # deploy history + per-replica status
lizard events --limit 25       # show more
lizard ps                      # current services, status, and URLs
```

[डैशबोर्ड](/dashboard) में हर सर्विस के **Overview** टैब पर उसके डिप्लॉय की लिस्ट होती है। किसी डिप्लॉय की स्थिति, सोर्स, बिल्ड लॉग और रीस्टार्ट देखने के लिए उसे खोलें।

<span id="restarts-vs-redeploys" />

## रीस्टार्ट बनाम रीडिप्लॉय

| कमांड | यह क्या करती है |
|---------|--------------|
| `lizard restart --service <svc>` | **मौजूदा** बिल्ड का रीस्टार्ट: रीबिल्ड नहीं |
| `lizard redeploy --service <svc>` | लेटेस्ट कमिट/अपलोड से **नया बिल्ड**, फिर रिलीज़ |

[`lizard restart`](/cli/restart) और [`lizard redeploy`](/cli/redeploy) देखें। रेप्लिका रीस्टार्ट करने के लिए `restart` का उपयोग करें (जैसे ऐसा रनटाइम सीक्रेट लेने के लिए जो हॉट-रीलोड नहीं हुआ); नया बिल्ड चाहिए तो `redeploy` का।

<span id="recovering-from-a-crash" />

## क्रैश के बाद रिकवरी

सबसे हाल के क्रैश या रीस्टार्ट के लॉग देखें:

```bash
lizard logs --restart latest       # log tail around the latest restart
lizard logs --restart <id>         # a specific restart
lizard events                      # see replica status
```

<span id="config-changes-no-rebuild" />

## कॉन्फ़िगरेशन बदलाव (बिना रीबिल्ड)

ज़्यादातर एनवायरनमेंट वेरिएबल और सीक्रेट के बदलाव बिना रीबिल्ड के लागू होते हैं: Lizard सर्विस का कॉन्फ़िगरेशन अपडेट करके उसे रीस्टार्ट करता है, जिसमें कुछ सेकंड लगते हैं। बिल्ड-टाइम वैल्यूज़ (`VITE_*`, `NEXT_PUBLIC_*`) और बिल्ड फ़ील्ड्स में बदलाव चल रही सर्विस का रीबिल्ड ज़रूर करवाते हैं: [रीबिल्ड ट्रिगर्स की टेबल](/concepts/build-pipeline#what-triggers-a-rebuild) और [बिल्ड-टाइम वेरिएबल्स](/concepts/build-pipeline#build-time-variables) देखें।

<span id="failed-releases-and-recovery" />

## फ़ेल हुई रिलीज़ और रिकवरी

बिल्ड का फ़ेल होना और ऐप्लिकेशन का शुरू न हो पाना अलग-अलग मामले हैं। फ़ेल हुआ बिल्ड कुछ नहीं बदलता: चल रहा वर्ज़न सर्व करता रहता है। जब नया पॉड कभी रेडी नहीं होता, तो HTTP सर्विस अपना पिछला वर्ज़न सर्व करती रहती है, और नए पॉड को कोई ट्रैफ़िक नहीं मिलता। वर्कर्स और अटैच वॉल्यूम वाली सर्विसेज़ नया पॉड शुरू होने से पहले पुराना पॉड बंद कर देती हैं, इसलिए जो रिलीज़ कभी रेडी नहीं होती, वह उन्हें डाउन छोड़ देती है। एक्टिव सर्विस, बिल्ड लॉग और रनटाइम लॉग जाँचें। `lizard redeploy` चुने गए सोर्स को फिर से बिल्ड करता है; यह पिछला बिल्ड वापस लाने की कमांड नहीं है। ज़रूरत हो तो सोर्स कमिट को रिवर्ट करें, उसे डिप्लॉय करें और नतीजा जाँचें। [ज्ञात समस्याएँ](/platform/known-issues) देखें।
