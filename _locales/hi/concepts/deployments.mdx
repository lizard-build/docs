# डिप्लॉयमेंट्स

एक **डिप्लॉयमेंट** एक सेवा का एक बिल्ड-और-रिलीज़ है। सेवाएँ Kubernetes पॉड्स के रूप में चलती हैं। एक सफल बिल्ड अपने आप यह साबित नहीं करता है कि एप्लिकेशन शुरू हो गया है या अनुरोधों को सर्व कर सकता है।

<span id="how-a-deploy-happens" />

## डिप्लॉय कैसे होता है

ये क्रियाएँ एक डिप्लॉयमेंट शुरू करती हैं:

- ट्रैक की गई ब्रांच के लिए एक **`git push`** (`github`-स्रोत सेवाओं के लिए)।
- **`lizard redeploy`**: नवीनतम कमिट (git) या अंतिम अपलोड से वर्तमान चर के साथ फिर से बनाएँ।
- **`lizard up`**: वर्तमान डायरेक्टरी अपलोड करें और इसे डिप्लॉय करें।
- एक **`service set`** जो बिल्ड-प्रभावित फ़ील्ड को बदलता है।

```bash
lizard redeploy --service api      # rebuild + redeploy from current source
lizard up                          # upload cwd and deploy
```

<span id="lifecycle" />

## लाइफसाइकिल

1. **बिल्ड**: प्लेटफ़ॉर्म आपके बिल्ड को चलाता है ( [बिल्ड पाइपलाइन](/concepts/build-pipeline) देखें)।
2. **प्री-डिप्लॉय**: यदि `preDeployCommand` और `startCommand` दोनों सेट हैं, तो कंटेनर `sh -c "<pre> && exec <start>"` चलाता है। प्री-डिप्लॉय कमांड हर कंटेनर (प्रत्येक प्रतिकृति, प्रत्येक पुनरारंभ) की शुरुआत में चलता है, इसलिए इसे कई बार और एक साथ चलाने के लिए सुरक्षित बनाएँ। `startCommand` के बिना इसे छोड़ दिया जाता है।
3. **स्टार्ट**: Lizard नए पॉड को पुराने वाले के बगल में शुरू करता है। [वर्कर्स](/deploy/workers) और [वॉल्यूम](/cli/volume) से जुड़ी सेवाएँ पहले पुराने पॉड को रोक देती हैं, इसलिए वे हर डिप्लॉय और पुनरारंभ पर थोड़े समय के लिए डाउन रहती हैं।
4. **हेल्थ चेक**: एक TCP प्रोब हर 2 सेकंड में ऐप के पोर्ट की जाँच करता है, और ट्रैफ़िक केवल एक तैयार पॉड में जाता है। Lizard इसके लिए लगभग 30 सेकंड तक प्रतीक्षा करता है; यदि नया पॉड तब तक तैयार नहीं होता है, तो डिप्लॉय को विफल चिह्नित किया जाता है। वर्कर्स प्रोब को छोड़ देते हैं।
5. **सत्यापित करें**: रिलीज़ की स्थिति का निरीक्षण करें और एप्लिकेशन URL को कॉल करें। पोर्ट पहुंच योग्यता एक पूर्ण एप्लिकेशन स्वास्थ्य जांच नहीं है।

<span id="streaming-output" />

## आउटपुट स्ट्रीमिंग

जब आप एक नॉन-डिटैच्ड `lizard up` (या `redeploy`) चलाते हैं, तो बिल्ड लॉग लाइव स्ट्रीम होते हैं। `lizard up --json` के साथ, आपको प्रति लाइन एक JSON इवेंट मिलता है:

```json
{ "event": "log", "line": "..." }
{ "event": "deployed", "status": "...", "url": "https://..." }
```

अंतिम इवेंट `deployed`, `failed`, या `deploying` है। `lizard redeploy --json` कोई लॉग लाइन प्रिंट नहीं करता है: यह एक बार में एक ऑब्जेक्ट (`status: "deploying"`) लौटाता है, या, `--wait` के साथ, अंत में `ok` और अंतिम `status` के साथ एक ऑब्जेक्ट। डिप्लॉय शुरू करने और तुरंत वापस लौटने के लिए `--detach` का उपयोग करें।

<span id="inspecting-history" />

## इतिहास का निरीक्षण करना

```bash
lizard events                  # deploy history + per-replica status
lizard events --limit 25       # show more
lizard ps                      # current services, status, and URLs
```

डैशबोर्ड](/dashboard) में, प्रत्येक सर्विस के **Overview** टैब पर उसके डिप्लॉय की सूची होती है। उसकी स्थिति, स्रोत, बिल्ड लॉग और रीस्टार्ट देखने के लिए एक खोलें।

<span id="restarts-vs-redeploys" />

## रीस्टार्ट बनाम रीडिप्लॉय

| कमांड | यह क्या करता है |
|---------|--------------|
| `lizard restart --service <svc>` | **वर्तमान** बिल्ड का रीस्टार्ट: कोई रीबिल्ड नहीं |
| `lizard redeploy --service <svc>` | नवीनतम कमिट/अपलोड से **ताज़ा बिल्ड**, फिर रिलीज़ |

[`lizard restart`](/cli/restart) और [`lizard redeploy`](/cli/redeploy) देखें। रेप्लिका को रीस्टार्ट करने के लिए `restart` का उपयोग करें (उदाहरण के लिए, रनटाइम सीक्रेट को पिकअप करने के लिए जिसे हॉट-रीलोड नहीं किया गया था); जब आपको नए बिल्ड की आवश्यकता हो तो `redeploy` का उपयोग करें।

<span id="recovering-from-a-crash" />

## क्रैश से उबरना

सबसे हालिया क्रैश या रीस्टार्ट के लॉग का निरीक्षण करें:

```bash
lizard logs --restart latest       # log tail around the latest restart
lizard logs --restart <id>         # a specific restart
lizard events                      # see replica status
```

<span id="config-changes-no-rebuild" />

## कॉन्फ़िगरेशन परिवर्तन (कोई रीबिल्ड नहीं)

अधिकांश एनवायरनमेंट वेरिएबल और सीक्रेट परिवर्तन बिना रीबिल्ड के लागू होते हैं: Lizard सर्विस के कॉन्फ़िगरेशन को अपडेट करता है और उसे रीस्टार्ट करता है, जिसमें कुछ सेकंड लगते हैं। बिल्ड-टाइम मान (`VITE_*`, `NEXT_PUBLIC_*`) और बिल्ड-फ़ील्ड परिवर्तन रनिंग सर्विस के रीबिल्ड को बाध्य करते हैं: [रीबिल्ड ट्रिगर तालिका](/concepts/build-pipeline#what-triggers-a-rebuild) और [बिल्ड-टाइम वैरिएबल](/concepts/build-pipeline#build-time-variables) देखें।

<span id="failed-releases-and-recovery" />

## विफल रिलीज़ और रिकवरी

एक असफल बिल्ड और एक असफल एप्लिकेशन स्टार्ट अलग-अलग मामले हैं। एक असफल बिल्ड कुछ भी नहीं बदलता है: रनिंग वर्शन सर्व करना जारी रखता है। जब कोई नया पॉड कभी तैयार नहीं होता है, तो एक HTTP सर्विस अपने पिछले वर्शन को सर्व करना जारी रखती है, और नए पॉड को कोई ट्रैफ़िक नहीं मिलता है। वर्कर और अटैच्ड वॉल्यूम वाली सर्विस नए पॉड के शुरू होने से पहले पुराने पॉड को रोक देती हैं, इसलिए एक रिलीज़ जो कभी तैयार नहीं होती है, उन्हें डाउन छोड़ देती है। एक्टिव सर्विस, बिल्ड लॉग और रनटाइम लॉग का निरीक्षण करें। `lizard redeploy` चयनित स्रोत को फिर से बनाता है; यह पिछले बिल्ड को बहाल करने के लिए कमांड नहीं है। आवश्यकतानुसार स्रोत कमिट को वापस करें, उसे डिप्लॉय करें, और परिणाम जांचें। [ज्ञात समस्याएँ](/platform/known-issues) देखें।
