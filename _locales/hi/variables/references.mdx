# क्रॉस-सर्विस रेफरेंस

रेफरेंस की मदद से कोई सर्विस क्रेडेंशियल्स कॉपी-पेस्ट किए बिना दूसरी सर्विस या ऐडऑन के मान पढ़ सकती है। हर मान एक ही जगह रहता है; उसे इस्तेमाल करने वाली सर्विसेज़ को बदलाव अपने अगले डिप्लॉय पर मिल जाते हैं।

<span id="syntax" />

## सिंटैक्स

```
${{<name>.<KEY>}}
```

- `<name>` — टारगेट सर्विस या ऐडऑन का नाम (वही जो डैशबोर्ड में दिखता है और `lizard add -n` में इस्तेमाल होता है)।
- `<KEY>` — वह की जिसे टारगेट एक्सपोज़ करता है। ऐडऑन अपने कनेक्शन मान एक्सपोज़ करता है। सर्विस अपने प्रोजेक्ट और सर्विस वेरिएबल व सीक्रेट्स, साथ ही अपने `LIZARD_*` और `PORT` मान एक्सपोज़ करती है। वह वे `DATABASE_URL` या `REDIS_URL` एक्सपोज़ नहीं करती जिन्हें Lizard ऐडऑन से उसमें इंजेक्ट करता है; इनके लिए सीधे ऐडऑन का रेफरेंस दें।

जहाँ भी कोई मान दिया जा सकता है, वहाँ इन्हें इस्तेमाल करें — आम तौर पर किसी सीक्रेट में:

```bash
lizard secrets set DATABASE_URL='${{postgres.DATABASE_URL}}' --service api
```

<span id="how-they-resolve" />

## रेफरेंस कैसे रिज़ॉल्व होते हैं

- रेफरेंस **डिप्लॉय के समय** टारगेट के एक्सपोज़ किए गए मानों से रिज़ॉल्व होते हैं।
- सीक्रेट में (`lizard secrets set` या डैशबोर्ड से) सेट किए गए रेफरेंस टारगेट के **मौजूदा नाम** से मैच होते हैं। टारगेट का नाम बदलने पर वे टूट जाते हैं; नाम बदलने के बाद हर `${{oldname.KEY}}` अपडेट करें। `lizard add -v` से बनाए गए रेफरेंस नाम बदलने के बाद भी टारगेट से जुड़े रहते हैं।
- **मौजूद न होने वाले** टारगेट या की का रेफरेंस **खाली स्ट्रिंग** बन जाता है — इससे डिप्लॉय फ़ेल *नहीं* होता। बिल्ड लॉग में हर खाली रेफरेंस के लिए कारण सहित चेतावनी दिखती है।
- सिर्फ़ **सर्कुलर** रेफरेंस पर एरर आता है।

> रेफरेंस जोड़ने के बाद बिल्ड लॉग में खाली रेफरेंस जाँचें:
> ```bash
> lizard logs --build --service api
> ```

अगर कोई रेफरेंस आपकी उम्मीद के मुताबिक नहीं दिख रहा, तो [समस्या निवारण → कोई सीक्रेट या रेफरेंस दिख नहीं रहा](/variables/troubleshooting/reference-not-applied) देखें।

<span id="common-patterns" />

## आम पैटर्न

**एक ऐडऑन को कई सर्विसेज़ से जोड़ें** — हर कंज्यूमर सर्विस पर अलग से बाइंड करें; प्रोजेक्ट के अंदर प्राइवेट URL इस्तेमाल करें:

```bash
lizard secrets set REDIS_URL='${{redis.REDIS_PRIVATE_URL}}' --service api
lizard secrets set REDIS_URL='${{redis.REDIS_PRIVATE_URL}}' --service worker
```

**दूसरी सर्विस के मान का रेफरेंस दें** — जैसे कोई कैलकुलेट किया हुआ URL या टोकन शेयर करने के लिए। `LIZARD_PUBLIC_DOMAIN` सिर्फ़ होस्टनेम होता है (बिना स्कीम के) और सर्विस को डोमेन मिलने के बाद ही मौजूद होता है; `LIZARD_PRIVATE_DOMAIN` (`<name>.lizard.internal`) से प्रोजेक्ट के अंदर सर्विस तक पहुँचा जा सकता है:

```bash
lizard secrets set UPSTREAM_URL='https://${{api.LIZARD_PUBLIC_DOMAIN}}' --service web
lizard secrets set INTERNAL_API='http://${{api.LIZARD_PRIVATE_DOMAIN}}:8080' --service web
```

**उसी टाइप के दूसरे ऐडऑन का रेफरेंस दें** — उसका जेनरेट किया गया नाम इस्तेमाल करें:

```bash
lizard secrets set CACHE_URL='${{redis-winter-otter.REDIS_URL}}' --service api
```

<span id="why-not-just-use---global" />

## सीधे `--global` क्यों न इस्तेमाल करें?

शेयर किए जाने वाले मान को प्रोजेक्ट (`--global`) स्कोप में रखने से वह *हर* सर्विस को दिखने लगता है, उन्हें भी जिन्हें उसकी ज़रूरत नहीं है। रेफरेंस मान को एक ही जगह रखता है और उसे सिर्फ़ वहीं बाइंड करता है जहाँ आपने उसे सेट किया है। ध्यान दें कि हर सर्विस को प्रोजेक्ट के Postgres और Redis ऐडऑन से पहले से ही एक `DATABASE_URL` और एक `REDIS_URL` मिलता है, सबसे कम प्राथमिकता पर; एक ही टाइप के कई ऐडऑन होने पर कौन-सा मिलेगा, यह तय नहीं है। रेफरेंस इन्हें ओवरराइड कर देता है। [सीक्रेट स्कोपिंग](/variables#scoping) देखें।
