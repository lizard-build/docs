# Bekannte Probleme

<span id="redeploy-is-not-rollback" />

Diese Seite dokumentiert Verhalten, das besondere Vorsicht oder eine verifizierte Freigabe erfordert. Ein zur Prüfung eingereichter Code-Fix ist keine Garantie für einen laufenden Dienst.

<span id="sandbox-pause-and-expiration" />

## Pause und Ablauf von Sandboxen

Erstellen Sie eine Sandbox, führen Sie Befehle aus und rufen Sie danach `kill` auf. `connect` verbindet mit einer bestehenden Sandbox, ohne ihren Zustand zu ändern; eine pausierte oder gestoppte Sandbox wird dadurch nicht fortgesetzt. Pause, Fortsetzen, Snapshot und Restore sind verfügbar; siehe [Pause, Fortsetzen und Snapshots](/sandboxes/quickstart#pause-and-resume). Fork (`sandbox.fork({ count })`) funktioniert bei Firecracker-Sandboxes; bei angehängtem Volume gibt es HTTP 409 zurück, bei einer Pod-Sandbox HTTP 501. `lizard sandbox ssh` öffnet eine interaktive Shell mit Ihren CLI-Zugangsdaten. Zugriff über das SSH-Protokoll gibt es nicht, daher funktionieren SSH-Clients, `scp` und Portweiterleitung nicht.

Eine Pause schließt offene Netzwerkverbindungen. Lassen sich die Prozesse nicht speichern, läuft die Sandbox weiter und meldet den Grund in `pauseError`. Eine pausierte Sandbox lässt sich nur auf ihrem eigenen Node fortsetzen; fällt dieser Node aus, geht der pausierte Zustand verloren.

Dateien und laufende Prozesse bleiben verfügbar, solange die Sandbox läuft. Nach dem Stopp kann eine spätere Sandbox nur Dateien auf einem angehängten Persistent Volume unter `/workspace` wiederverwenden. Ohne Volume ist `/workspace` temporär. Ein Volume hängt jeweils an einer Sandbox und liegt auf einem einzelnen Knoten. Exportieren Sie Dateien, die einen Knotenausfall überstehen müssen.

## Redeploy ist kein Rollback

`lizard redeploy` baut die ausgewählte Quelle mit der aktuellen Konfiguration erneut. Dabei wird kein vorheriger Build ausgewählt. Ein fehlgeschlagener Build und ein fehlgeschlagener Start haben unterschiedliche Auswirkungen; prüfen Sie den aktiven Dienst und seine Logs, bevor Sie einen Wiederherstellungsschritt wählen. Gehen Sie nicht davon aus, dass jede Runtime bei einem fehlgeschlagenen Start weiterhin das alte Release ausliefert.

<span id="dockerfile-precedence" />

## Vorrang des Dockerfile

Explizite Build- oder Start-Befehle haben Vorrang vor einem Dockerfile im Repository. Entfernen Sie diese Überschreibungen, wenn Sie `dockerfilePath` auswählen. Schon eine Aktualisierung der Einstellungen kann einen Build starten, prüfen Sie daher die Ereignisse, bevor Sie ein weiteres Redeploy auslösen. Siehe [Fehlerbehebung für Dockerfile](/deploy/troubleshooting/incomplete-dockerfile).

<span id="templates-and-mcp" />

## Vorlagen und MCP

Wählen Sie eine Vorlage aus dem aktuellen Katalog. Aktiviert sind `base`, `interpreter`, `codex`, `desktop`, `opencode`, `pi`, `prime` und `claude`; die Verfügbarkeit hängt von Region und Pool-Kapazität ab. `interpreter` enthält Python und gängige Datenbibliotheken. Prüfen Sie die Werkzeugversionen in der Sandbox. Die öffentliche CLI bietet keinen Upload eigener Vorlagen.

Lizard Skill verwendet Lizard CLI und stellt keinen MCP-Transport bereit. Für MCP-Clients verwenden Sie den gehosteten Lizard MCP Server; siehe [Lizard MCP](/agents#lizard-mcp). Das Hosting eines eigenen entfernten MCP-Servers ist ein separates Application-Deployment; siehe den [Leitfaden](/guides/deploy-mcp-server).

<span id="service-port-changes-fixed-and-verified-on-2026-09-09" />

## Änderungen am Service-Port: behoben und verifiziert am 2026-09-09

Die Prüfung vom 7. September ergab HTTP 503, nachdem ein Upload-Dienst von Port `3000` auf `80` geändert wurde, obwohl ein bereiter Prozess vorhanden war. Der Fix in Produktion wendet den gewählten Port jetzt auf den laufenden Dienst an und behält einen expliziten Port beim Upload und beim Rebuild bei. Eine Live-Prüfung der Portänderung war am 9. September erfolgreich. Prüfen Sie nach einem Deployment sowohl die öffentliche URL als auch den Zustand des Dienstes.

<span id="upload-archives-and-failed-build-exit-codes-fixed" />

## Upload-Archive und Exit-Codes bei fehlgeschlagenen Builds: behoben

Lizard CLI 0.3.95 schließt macOS-`._*`-Metadateneinträge aus Source-Uploads aus und gibt bei fehlgeschlagenen Cloud-Builds einen Exit-Code ungleich null zurück. Aktualisieren Sie ältere CLI-Versionen; `COPYFILE_DISABLE` wird nicht mehr benötigt. Die [Framework-Prüfungen](/framework-guides/validation) decken Uploads von macOS mit der aktuellen CLI ab.

Ein erfolgreicher Build allein beweist noch nicht, dass die App funktioniert. Prüfen Sie nach dem Deployment die öffentliche URL, Routen, Formulare und Datenoperationen.
