# Dienstübergreifende Referenzen

Mit Referenzen kann ein Dienst die Werte eines anderen Dienstes oder Add-ons lesen, ohne Credentials per Copy-and-paste zu duplizieren. Sie halten jeden Wert an einer Stelle; Consumer übernehmen Änderungen beim nächsten Deploy.

## Syntax

```
${{<name>.<KEY>}}
```

- `<name>` — der Name des Zieldienstes oder Add-ons (der im Dashboard angezeigt und in `lizard add -n` verwendet wird).
- `<KEY>` — ein Schlüssel in der zusammengeführten Umgebung des Ziels.

Verwende sie überall dort, wo ein Wert akzeptiert wird — am häufigsten in einem Secret:

```bash
lizard secrets set DATABASE_URL='${{postgres.DATABASE_URL}}' --service api
```

<span id="how-they-resolve" />

## Wie sie aufgelöst werden

- Referenzen werden zur **Deploy-Zeit** anhand der zusammengeführten Umgebung des Ziels aufgelöst.
- Sie beziehen sich auf den **aktuellen Namen** des Ziels. Ein Umbenennen des Ziels macht sie kaputt; aktualisiere nach einer Umbenennung jedes `${{oldname.KEY}}`.
- Eine Referenz auf ein **fehlendes** Ziel oder einen fehlenden Schlüssel wird zu einem **leeren String** aufgelöst — das Bereitstellen schlägt dadurch *nicht* fehl. Das Build-Log gibt für jede leere Referenz eine Warnung mit der Ursache aus.
- Nur **zirkuläre** Referenzen werfen einen Fehler.

> Prüfe nach dem Einrichten einer Referenz im Build-Log, ob leere Referenzen vorhanden sind:
> ```bash
> lizard logs --build --service api
> ```

Wenn eine Referenz nicht wie erwartet erscheint, siehe [Troubleshooting → ein Secret oder eine Referenz wird nicht angezeigt](/variables/troubleshooting/reference-not-applied).

<span id="common-patterns" />

## Häufige Muster

**Ein Add-on mit mehreren Diensten verbinden** — auf jedem Consumer binden; verwende innerhalb des Projekts die private URL:

```bash
lizard secrets set REDIS_URL='${{redis.REDIS_PRIVATE_URL}}' --service api
lizard secrets set REDIS_URL='${{redis.REDIS_PRIVATE_URL}}' --service worker
```

**Einen Wert aus einem anderen Dienst referenzieren** — z. B. eine berechnete URL oder ein Token teilen. `LIZARD_PUBLIC_DOMAIN` ist ein reiner Hostname und existiert, sobald der Dienst eine Domain hat; `LIZARD_PRIVATE_DOMAIN` (`<name>.lizard.internal`) erreicht den Dienst innerhalb des Projekts:

```bash
lizard secrets set UPSTREAM_URL='https://${{api.LIZARD_PUBLIC_DOMAIN}}' --service web
lizard secrets set INTERNAL_API='http://${{api.LIZARD_PRIVATE_DOMAIN}}:8080' --service web
```

**Ein zweites Add-on desselben Typs referenzieren** — verwende seinen generierten Namen:

```bash
lizard secrets set CACHE_URL='${{redis-winter-otter.REDIS_URL}}' --service api
```

<span id="why-not-just-use---global" />

## Warum nicht einfach `--global` verwenden?

Wenn du einen gemeinsamen Wert im Projektbereich (`--global`) ablegst, ist er für *jeden* Dienst sichtbar, auch für solche, die ihn nicht benötigen. Eine Referenz hält den Wert an einer Stelle und bindet ihn nur dort, wo du sie setzt. Beachte, dass `DATABASE_URL` und `REDIS_URL` jedes laufenden Postgres- und Redis-Add-ons ohnehin jeden Dienst erreichen, und zwar mit der niedrigsten Priorität; eine Referenz überschreibt sie. Siehe [Secret-Scopes](/variables#scoping).
