# Verwaltete Addons

Lizard stellt **Managed Postgres**, **Managed Redis** und S3-kompatiblen **Managed Object Storage** mit einem einzigen Befehl bereit. Jedes Add-on befindet sich in Ihrem Projekt, stellt einen festen Satz von Umgebungsvariablen bereit und wird von Ihren Services über [Referenzen](/concepts/architecture#cross-resource-references) verwendet.

<span id="provision-an-addon" />

## Ein Add-on bereitstellen

```bash
lizard add postgres            # one addon
lizard add postgres redis s3   # several at once
lizard add --list              # show available types
```

<span id="naming" />

## Benennung

Das **erste** Add-on eines bestimmten Typs erhält den bloßen Typ als Namen — daher funktioniert `${{postgres.DATABASE_URL}}` sofort. Zusätzliche Addons desselben Typs erhalten einen generierten Namen wie `postgres-autumn-bear`. Ein gelöschtes Add-on behält seinen Namen 3 Tage lang im Papierkorb, sodass ein in diesem Zeitraum hinzugefügtes neues Add-on einen generierten Namen erhält; stellen Sie das alte wieder her oder richten Sie die Referenzen auf den neuen Namen aus.

Es gibt keinen Fallback über einen Typ-Alias: Eine Referenz muss den **aktuellen** Namen des Addons verwenden. Das Umbenennen eines Add-ons bricht Referenzen auf den alten Namen, aktualisieren Sie diese daher nach einer Umbenennung:

```bash
lizard service rename main-db --service postgres   # addons rename through the same command
lizard secrets set DATABASE_URL='${{main-db.DATABASE_URL}}' --service api
```

<span id="consuming-an-addon" />

## Ein Add-on verwenden

Referenzieren Sie die Variablen eines Addons aus jedem Service. Die Referenz wird beim Bereitstellen aufgelöst, sodass der Service beim nächsten Deployment die aktuellen Werte des Addons übernimmt:

```bash
lizard secrets set DATABASE_URL='${{postgres.DATABASE_URL}}' --service api
lizard redeploy --service api
```

Lizard injiziert außerdem `DATABASE_URL` und `REDIS_URL` von jedem laufenden Postgres- und Redis-Add-on in jeden Service des Projekts, und zwar mit der niedrigsten Priorität. Eine explizite Referenz überschreibt sie und wählt ein bestimmtes Add-on aus. Für Services im selben Projekt sollten Sie die private URL bevorzugen:

```bash
lizard secrets set DATABASE_URL='${{postgres.DATABASE_PRIVATE_URL}}' --service api
```

Siehe [Secret-Scoping](/variables#scoping).

<span id="variables-by-type" />

## Variablen nach Typ

| Add-on | Variablen |
|-------|-----------|
| **postgres** | `DATABASE_URL`, `DATABASE_PRIVATE_URL`, `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`, `PGDATABASE`, `POSTGRES_USER`, `POSTGRES_DB`, `POSTGRES_PASSWORD` |
| **redis** | `REDIS_URL`, `REDIS_PRIVATE_URL` |
| **s3** | `S3_ENDPOINT`, `S3_DEFAULT_BUCKET`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, `S3_REGION` |

`DATABASE_URL` und `REDIS_URL` verwenden den öffentlichen Endpunkt. `DATABASE_PRIVATE_URL` und `REDIS_PRIVATE_URL` verwenden `<name>.lizard.internal` im [privaten Netzwerk](/networking#private-networking) und funktionieren nur von Services im selben Projekt aus.

<span id="dashboard-browsers" />

## Browser im Dashboard

Das [Dashboard](/dashboard) enthält einen Datenbrowser für jedes Add-on — einen SQL-/Tabellen-Editor für Postgres, einen Key-Browser für Redis und einen Bucket-/Objekt-Browser für S3 — sodass Sie Daten prüfen und bearbeiten können, ohne Lizard zu verlassen.

<span id="storage" />

## Speicher

Daten-Volumes von Postgres und Redis sind **nur erweiterbar**. Erhöhen Sie die Kapazität mit:

```bash
lizard scale --service postgres --storage 8192
```
