# lizard up

Das aktuelle Verzeichnis hochladen und bereitstellen.

<span id="usage" />

## Verwendung

```bash
lizard up [path] [flags]
```

`up` paketiert Ihren Arbeitsbaum (oder `path`) als Tarball, sendet ihn an die Build-Knoten und stellt ihn bereit. Es erzwingt `sourceType=upload` auf dem Zieldienst, streamt Build-Logs über SSE und gibt nach Abschluss die Live-URL aus.

Wenn das aktuelle Verzeichnis noch nicht mit einem Projekt verknüpft ist, führt `up` zuerst `init` aus. In einem TTY ist das interaktiv; in einer Nicht-TTY-Umgebung (CI) wird **nicht** stillschweigend ein Projekt erstellt — stattdessen wird ein Fehler ausgegeben und Sie werden aufgefordert, `lizard init --name <project>` auszuführen (oder `--project <project>` an `up` zu übergeben), damit nicht durch einen Tippfehler ein leeres Projekt erzeugt wird.

## Flags

| Flag | Beschreibung |
|------|-------------|
| `-s, --service <name>` | Einen vorhandenen Dienst als Ziel verwenden |
| `-p, --project <id>` | Projektname, Slug oder ID |
| `--build-command <cmd>` | Den Build-Befehl überschreiben |
| `--start-command <cmd>` | Den Startbefehl überschreiben |
| `--pre-deploy-command <cmd>` | Vor dem Startbefehl bei jedem Containerstart ausführen (jedes Replikat, jeder Neustart). Erfordert einen Startbefehl; er sollte sich gefahrlos mehrfach ausführen lassen |
| `--port <number>` | Container-Port (`0` = Worker-Modus). Neue Dienste verwenden standardmäßig `3000`, sofern nicht ein `EXPOSE` im Dockerfile den Port festlegt |
| `--region <code>` | Region für einen neuen Dienst; bei einem vorhandenen Dienst wird sie ignoriert |
| `-d, --detach` | Das Bereitstellen starten und beenden, ohne Logs zu streamen |
| `-c, --ci` | Nur Build-Logs streamen und beenden, sobald der Build endet |
| `--no-gitignore` | Alles hochladen und `.gitignore` ignorieren |

<span id="subcommands" />

## Unterbefehle

### `lizard up status <app-id>`

Den Status, die URL und den Status des letzten Builds eines Dienstes anzeigen. Übergeben Sie die Dienst-ID, die `up --detach` ausgibt.

## Beispiele

<span id="deploy-the-current-directory" />

### Das aktuelle Verzeichnis bereitstellen

```bash
lizard up
```

<span id="deploy-to-a-specific-service-with-a-custom-start-command-and-port" />

### Auf einem bestimmten Dienst mit benutzerdefiniertem Startbefehl und Port bereitstellen

Erstellen Sie den benannten Dienst zuerst mit `lizard add --service api`, falls er nicht existiert.

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

<span id="deploy-headlessly-in-ci" />

### Headless in CI bereitstellen

```bash
export LIZARD_TOKEN=liz_xxx
lizard init --name my-project
lizard add --service api
lizard up --ci --service api
```

Überspringen Sie `lizard add`, wenn der Dienst bereits existiert. Ein fehlgeschlagener Build oder Deploy endet mit Exit-Code `1`. Mit `--ci` bezieht sich der Exit-Code nur auf den Build. Prüfen Sie daher `lizard ps --json`, bevor Sie das Release als abgeschlossen markieren. `--detach` endet mit `0`, sobald der Upload akzeptiert wurde. Siehe [Framework-Setup](/framework-guides#prepare-the-project).
