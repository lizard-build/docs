# lizard up

Das aktuelle Verzeichnis hochladen und bereitstellen.

<span id="usage" />

## Verwendung

```bash
lizard up [path] [flags]
```

`up` paketiert Ihren Arbeitsbaum (oder `path`) als Tarball, sendet ihn an die Build-Knoten und stellt ihn bereit. Es erzwingt `sourceType=upload` auf dem Zieldienst, streamt Build-Logs über SSE und gibt nach Abschluss die Live-URL aus.

Ist das Verzeichnis mit keinem Projekt verknüpft, verknüpft `up` es mit dem Standardprojekt Ihres Kontos (dem ältesten Projekt in Ihrem persönlichen Workspace) und stellt dort bereit, in einem TTY wie in CI. Um woanders bereitzustellen, führen Sie zuerst `lizard init --name <project>` aus oder übergeben Sie `--project`.

<span id="which-service-up-deploys-to" />

### In welchen Dienst `up` bereitstellt

1. In den Dienst, den Sie mit `--service` nennen. Hat das Projekt keinen Dienst mit diesem Namen, erstellt `up` ihn.
2. In den mit dem Verzeichnis verknüpften Dienst.
3. Sonst in einen Dienst, der nach dem `name` in `package.json` (ohne Scope) oder nach dem Verzeichnis benannt ist. In einem TTY fragt `up` nach dem Namen und schlägt diesen vor.

Hat das Projekt im letzten Fall schon einen Dienst mit diesem Namen, stellt `up` in ihn bereit. Jedes `up` stellt sein Ziel auf Upload-Quelle um, sodass ein GitHub-Dienst bei Push nicht mehr bereitstellt. Übergeben Sie `--service`, um das Ziel selbst zu wählen.

## Flags

| Flag | Beschreibung |
|------|-------------|
| `-s, --service <name>` | Dienst, in den bereitgestellt wird (Standard: der verknüpfte Dienst). Gibt es keinen mit diesem Namen, erstellt `up` ihn |
| `-p, --project <id>` | Projektname, Slug oder ID. In einem nicht verknüpften Verzeichnis verknüpft `up` das Verzeichnis damit und erstellt das Projekt, falls keines so heißt |
| `--build-command <cmd>` | Den Build-Befehl überschreiben |
| `--start-command <cmd>` | Den Startbefehl überschreiben |
| `--pre-deploy-command <cmd>` | Vor dem Startbefehl bei jedem Containerstart ausführen (jedes Replikat, jeder Neustart). Erfordert einen Startbefehl; er sollte sich gefahrlos mehrfach ausführen lassen |
| `--port <number>` | Container-Port (`0` = Worker-Modus). Neue Dienste verwenden standardmäßig `3000`, sofern nicht ein `EXPOSE` im Dockerfile den Port festlegt |
| `--region <code>` | Region für einen neuen Dienst; bei einem vorhandenen Dienst wird sie ignoriert |
| `-d, --detach` | Das Bereitstellen starten und beenden, ohne Logs zu streamen |
| `-c, --ci` | Nur Build-Logs streamen und beenden, sobald der Build endet |
| `--no-gitignore` | Alles hochladen und `.gitignore` ignorieren |

<span id="subcommands" />

## Unterbefehle

### `lizard up status <app-id>`

Den Status, die URL und den Status des letzten Builds eines Dienstes anzeigen. Übergeben Sie die Dienst-ID, die `up --detach` ausgibt.

## Beispiele

<span id="deploy-the-current-directory" />

### Das aktuelle Verzeichnis bereitstellen

```bash
lizard up
```

<span id="deploy-to-a-specific-service-with-a-custom-start-command-and-port" />

### Auf einem bestimmten Dienst mit benutzerdefiniertem Startbefehl und Port bereitstellen

Gibt es `api` noch nicht, erstellt `up` den Dienst.

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

<span id="deploy-headlessly-in-ci" />

### Headless in CI bereitstellen

```bash
export LIZARD_TOKEN=liz_xxx
lizard init --name my-project
lizard up --ci --service api   # creates api on the first run
```

Ein fehlgeschlagener Build oder Deploy endet mit Exit-Code `1`. Mit `--ci` bezieht sich der Exit-Code nur auf den Build. Prüfen Sie daher `lizard ps --json`, bevor Sie das Release als abgeschlossen markieren. `--detach` endet mit `0`, sobald der Upload akzeptiert wurde. Siehe [Framework-Setup](/framework-guides#prepare-the-project).
