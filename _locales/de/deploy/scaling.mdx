<span id="scaling" />

# Skalierung

Mit `lizard scale` fügen Sie einem Service Replikate hinzu, erhöhen CPU oder Arbeitsspeicher oder erweitern den Add-on-Speicher. Um einen Service auf null zu skalieren, lassen Sie ihn [im Leerlauf schlafen](#sleep-when-idle) oder [pausieren Sie ihn](#pause-a-service).

<span id="scale-a-service" />

## Einen Service skalieren

```bash
lizard scale --service api --replicas 3
lizard scale --service api --cpu 2 --memory 2048
```

| Flag | Gilt für | Zulässige Werte |
|------|-----------|----------------|
| `--replicas <n>` | Apps | `1` bis zum [Limit](/platform/limits#applications) Ihres Plans: `1` in der Testphase, `5` in jedem bezahlten Plan und in Enterprise |
| `--cpu <cores>` | Apps und Addons | ganze Kerne: `1`, `2`, `3`, `4` |
| `--memory <mb>` | Apps und Addons | `128`–`8192` MB (in 1-MB-Schritten) |
| `--storage <mb>` | **nur Addons**, nur vergrößern | `512`, `1024`, `2048`, `4096`, `8192`, `16384` |

Sie können Flags in einem einzelnen Befehl kombinieren. Änderungen an Replikaten werden ohne Rebuild ausgerollt. Änderungen an CPU und Arbeitsspeicher starten den Service mit den neuen Limits neu.

<span id="horizontal-scaling" />

## Horizontale Skalierung

Führen Sie mehrere Replikate einer App hinter dem Load Balancer aus:

```bash
lizard scale --service api --replicas 5
```

Jedes Replikat ist ein eigener Pod. Stellen Sie sicher, dass Ihre App zustandslos ist (speichern Sie den Zustand in [Managed Postgres](/addons/postgres), [Managed Redis](/addons/redis) oder [Managed Object Storage](/addons/storage)), damit Replikate austauschbar sind.

<span id="vertical-scaling" />

## Vertikale Skalierung

Geben Sie einem einzelnen Replikat mehr Ressourcen:

```bash
lizard scale --service api --cpu 4 --memory 8192
```

<span id="growing-addon-storage" />

## Add-on-Speicher erweitern

Add-on-Daten-Volumes können **nur vergrößert** werden — Sie können den Speicher erhöhen, aber nicht verkleinern:

```bash
lizard scale --service postgres --storage 8192
```

<span id="sleep-when-idle" />

## Im Leerlauf schlafen lassen

`lizard sleep --on` lässt einen Webservice schlafen, wenn er keinen Traffic bekommt, und weckt ihn bei der nächsten Anfrage in etwa einer Sekunde auf. Standardmäßig schläft er nach 10 Minuten ohne Traffic; mit `--idle` stellen Sie 5 bis 1440 Minuten ein. Das Einschalten startet den Service einmal neu. Es funktioniert nur für einen Service mit Port und einem Replikat, also nicht für Worker. Managed Postgres und Managed Redis können ebenfalls schlafen.

```bash
lizard sleep --on --idle 30 --service api
lizard sleep --off --service api    # always on
```

Siehe [`lizard sleep`](/cli/sleep).

<span id="pause-a-service" />

## Einen Service pausieren

`lizard pause` stoppt einen Service oder eine Datenbank, ohne etwas zu löschen: Die Ressource wird auf null skaliert und behält URL, Passwort, Einstellungen und Daten. `lizard resume` startet sie wieder. Ein pausierter GitHub-Service ignoriert Pushes, bis Sie ihn fortsetzen.

```bash
lizard pause api
lizard resume api
```

Um jeden Service in einem Projekt oder Workspace zu pausieren, nutzen Sie `lizard project pause` oder `lizard workspace pause`. Siehe [`lizard pause`](/cli/pause).

<span id="verifying" />

## Prüfung

```bash
lizard ps                 # replica status + URL
lizard events             # deploy history + current replicas
lizard metrics            # live CPU / memory / network / disk
lizard metrics --cost     # cost instead of metrics
```

Eine Änderung der Replikate erzeugt keinen Deploy, daher listet `lizard events` sie nicht auf; prüfen Sie stattdessen die Tabelle Replicas.
