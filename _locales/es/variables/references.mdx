# Referencias entre servicios

Las referencias permiten que un servicio lea los valores de otro servicio o addon sin copiar y pegar credenciales. Mantienen cada valor en un solo lugar; los consumidores recogen los cambios en su siguiente despliegue.

<span id="syntax" />

## Sintaxis

```
${{<name>.<KEY>}}
```

- `<name>` — el nombre del servicio o addon de destino (el que se muestra en el dashboard y se usa en `lizard add -n`).
- `<KEY>` — una clave que expone el destino. Un addon expone sus valores de conexión. Un servicio expone sus variables y secretos de proyecto y de servicio, además de sus valores `LIZARD_*` y `PORT`. No expone el `DATABASE_URL` ni el `REDIS_URL` que Lizard inyecta desde los addons; para esos, haz referencia al addon.

Úsalas en cualquier lugar donde se acepte un valor; lo más habitual es en un secreto:

```bash
lizard secrets set DATABASE_URL='${{postgres.DATABASE_URL}}' --service api
```

<span id="how-they-resolve" />

## Cómo se resuelven

- Las referencias se resuelven en el **momento del despliegue** usando los valores que expone el destino.
- Las referencias que defines en un secreto (`lizard secrets set` o el dashboard) coinciden con el **nombre actual** del destino. Cambiar el nombre del destino las rompe; actualiza cada `${{oldname.KEY}}` después de un cambio de nombre. Las referencias creadas con `lizard add -v` siguen al destino tras un cambio de nombre.
- Una referencia a un destino o clave **inexistente** se resuelve como una **cadena vacía**: *no* hace fallar el despliegue. El log de compilación muestra un aviso por cada referencia vacía, con el motivo.
- Solo las referencias **circulares** producen un error.

> Después de conectar una referencia, busca referencias vacías en el log de compilación:
> ```bash
> lizard logs --build --service api
> ```

Si una referencia no aparece como esperas, consulta [Solución de problemas → no aparece un secreto o referencia](/variables/troubleshooting/reference-not-applied).

<span id="common-patterns" />

## Patrones habituales

**Conecta un addon a varios servicios**: vincúlalo en cada consumidor; usa la URL privada dentro del proyecto:

```bash
lizard secrets set REDIS_URL='${{redis.REDIS_PRIVATE_URL}}' --service api
lizard secrets set REDIS_URL='${{redis.REDIS_PRIVATE_URL}}' --service worker
```

**Haz referencia al valor de otro servicio**: por ejemplo, comparte una URL calculada o un token. `LIZARD_PUBLIC_DOMAIN` es un hostname sin más y existe cuando el servicio tiene un dominio; `LIZARD_PRIVATE_DOMAIN` (`<name>.lizard.internal`) llega al servicio dentro del proyecto:

```bash
lizard secrets set UPSTREAM_URL='https://${{api.LIZARD_PUBLIC_DOMAIN}}' --service web
lizard secrets set INTERNAL_API='http://${{api.LIZARD_PRIVATE_DOMAIN}}:8080' --service web
```

**Haz referencia a un segundo addon del mismo tipo**: usa su nombre generado:

```bash
lizard secrets set CACHE_URL='${{redis-winter-otter.REDIS_URL}}' --service api
```

<span id="why-not-just-use---global" />

## ¿Por qué no usar simplemente `--global`?

Poner un valor compartido en el ámbito del proyecto (`--global`) lo expone a *todos* los servicios, incluidos los que no lo necesitan. Una referencia mantiene el valor en un solo lugar y lo vincula solo donde lo configuras. Ten en cuenta que cada servicio ya recibe un `DATABASE_URL` y un `REDIS_URL` de los addons de Postgres y Redis del proyecto, con la precedencia más baja; si hay varios addons del mismo tipo, no está definido cuál. Una referencia los sobrescribe. Consulta [Alcance de secretos](/variables#scoping).
