# lizard up

Sube el directorio actual y lo despliega.

<span id="usage" />

## Uso

```bash
lizard up [path] [flags]
```

`up` empaqueta tu árbol de trabajo (o `path`) como un tarball, lo envía a los nodos de compilación y lo despliega. Fuerza `sourceType=upload` en el servicio de destino, transmite los logs de compilación por SSE e imprime la URL activa al terminar.

Si el directorio no está vinculado a un proyecto, `up` lo vincula al proyecto predeterminado de tu cuenta (el proyecto más antiguo de tu workspace personal) y despliega ahí, tanto en un TTY como en CI. Para desplegar en otro sitio, ejecuta primero `lizard init --name <project>` o pasa `--project`.

<span id="which-service-up-deploys-to" />

### En qué servicio despliega `up`

1. En el servicio que indicas con `--service`. Si el proyecto no tiene un servicio con ese nombre, `up` lo crea.
2. En el servicio vinculado al directorio.
3. Si no, en un servicio con el `name` de `package.json` (sin el scope) o con el nombre del directorio. En un TTY, `up` pide el nombre y ofrece este.

En este último caso, si el proyecto ya tiene un servicio con ese nombre, `up` despliega en él. Cada `up` cambia su destino a origen upload, así que un servicio de GitHub deja de desplegarse con cada push. Pasa `--service` para elegir el destino tú mismo.

<span id="flags" />

## Banderas

| Bandera | Descripción |
|------|-------------|
| `-s, --service <name>` | Servicio en el que desplegar (por defecto, el vinculado). Si no hay ninguno con ese nombre, `up` lo crea |
| `-p, --project <id>` | Nombre, slug o ID del proyecto. En un directorio sin vincular, `up` vincula el directorio a él y lo crea si ningún proyecto tiene ese nombre |
| `--build-command <cmd>` | Sobrescribe el comando de compilación |
| `--start-command <cmd>` | Sobrescribe el comando de inicio |
| `--pre-deploy-command <cmd>` | Se ejecuta antes del comando de inicio cada vez que arranca un contenedor (cada réplica, cada reinicio). Requiere un comando de inicio; haz que sea seguro ejecutarlo muchas veces |
| `--port <number>` | Puerto del contenedor (`0` = modo worker). Los servicios nuevos usan `3000` por defecto, salvo que un `EXPOSE` del Dockerfile lo defina |
| `--region <code>` | Región para un servicio nuevo; se ignora en un servicio existente |
| `-d, --detach` | Inicia el despliegue y sale sin transmitir logs |
| `-c, --ci` | Transmite solo los logs de compilación y sale cuando termina la compilación |
| `--no-gitignore` | Sube todo, ignorando `.gitignore` |

<span id="subcommands" />

## Subcomandos

### `lizard up status <app-id>`

Muestra el estado de un servicio, su URL y el estado de su última compilación. Pasa el ID de servicio que imprime `up --detach`.

<span id="examples" />

## Ejemplos

<span id="deploy-the-current-directory" />

### Desplegar el directorio actual

```bash
lizard up
```

<span id="deploy-to-a-specific-service-with-a-custom-start-command-and-port" />

### Desplegar en un servicio específico con un comando de inicio y un puerto personalizados

Si `api` todavía no existe, `up` lo crea.

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

<span id="deploy-headlessly-in-ci" />

### Desplegar sin interacción en CI

```bash
export LIZARD_TOKEN=liz_xxx
lizard init --name my-project
lizard up --ci --service api   # creates api on the first run
```

Una compilación o un despliegue fallido sale con el código `1`. Con `--ci`, el código de salida solo cubre la compilación, así que revisa `lizard ps --json` antes de marcar la versión como terminada. `--detach` sale con `0` en cuanto se acepta la subida. Consulta [framework setup](/framework-guides#prepare-the-project).
