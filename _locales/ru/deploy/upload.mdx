# Развертывание из локального кода

Когда ваш код не на GitHub — или вы просто хотите итерироваться быстрее — загрузите текущую директорию напрямую с помощью `lizard up`. Она упаковывает вашу рабочую директорию в tarball, отправляет на узлы сборки и развертывает.

<span id="deploy-the-current-directory" />

## Развернуть текущую директорию

```bash
lizard up
```

- Загружает текущую директорию как tarball. Внутри git-репозитория учитывает `.gitignore` (отключается через `--no-gitignore`). Вне git пропускает только фиксированный список папок сборки и зависимостей (`node_modules`, `.git`, `dist`, `.next`, `build`, `__pycache__`, `.venv`, `venv`, `.cache`, `coverage`, `.turbo`, `.vercel`), а также `.DS_Store`, `*.pyc`, `*.pyo` и `*.log`, поэтому файлы `.env` загружаются. Предварительно выполните `git init` или уберите секреты из директории.
- Принудительно включает `sourceType=upload`.
- Выводит логи сборки через SSE и печатает живой URL по завершении.

Если директория ещё не привязана к проекту, `up` сначала запускает `init`. В интерактивном TTY это происходит в диалоговом режиме; в неинтерактивном (CI) проект **не** создаётся молча — команда выдаёт ошибку и просит выполнить `lizard init --name <project>` (или передать `--project <name>` в `up`). Это защищает от появления пустого проекта из-за опечатки.

<span id="common-flags" />

## Основные флаги

| Флаг | Назначение |
|------|----------|
| `-s, --service <name>` | Выбрать существующий сервис |
| `--build-command <cmd>` | Переопределить команду сборки |
| `--start-command <cmd>` | Переопределить команду запуска |
| `--pre-deploy-command <cmd>` | Запускать в начале каждого контейнера перед командой запуска; требует `--start-command` (см. [конфигурация сборки](/concepts/build-pipeline#build-configuration-reference)) |
| `--port <number>` | Порт контейнера (`0` = [режим воркера](/deploy/workers)) |
| `--region <code>` | Регион для нового сервиса (для существующих сервисов игнорируется) |
| `-d, --detach` | Запустить деплой и выйти без стриминга логов |
| `-c, --ci` | Вывод, дружественный к CI |
| `--no-gitignore` | Загрузить всё, игнорируя `.gitignore` |

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

<span id="setting-buildstart-commands" />

## Установка команд сборки и запуска

Передача `--build-command` или `--start-command` сохраняет её в сервисе и переключает сервис на путь **синтезированного Dockerfile**, если не задан `dockerfilePath`. На этом пути `Procfile` и `package.json` `scripts.start` **не** считываются — задавайте команду запуска явно. Подробнее в разделе [Конвейер сборки](/concepts/build-pipeline). Чаще всего это касается Python: [Django, Flask и FastAPI](https://lizard.build/blog/python-app-hosting#build-and-start-commands) требуют разную строку `gunicorn` или `uvicorn`.

<span id="re-deploying-an-upload-service" />

## Повторное развертывание upload-сервиса

`lizard up` повторно загружает и пересобирает. Чтобы пересобрать **последнюю** загрузку с текущими переменными без повторной загрузки:

```bash
lizard redeploy --service api
```

## Headless / CI

Для неинтерактивных сценариев явно привяжите проект перед деплоем:

```bash
export LIZARD_TOKEN=liz_xxx   # create one with: lizard keys create <name>
lizard init --name my-project
lizard up --ci --service api
```

<span id="when-to-prefer-github-instead" />

## Когда лучше выбрать GitHub

Загрузка отлично подходит для быстрой итерации и ситуаций без удалённого репозитория. Для всего долгоживущего предпочитайте [источник из GitHub](/deploy/github), чтобы пуши автоматически переразвертывали приложение и у вас была чистая история деплоев.
