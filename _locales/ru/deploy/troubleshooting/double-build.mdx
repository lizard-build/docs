# Переразвёртывание отменило сборку, которую запустило моё изменение

Вы выполнили `lizard service set` для изменения поля, затем `lizard redeploy`. Деплой занял больше времени, чем ожидалось, а в истории может быть отменённая сборка.

<span id="what-this-means" />

## Что это значит

Вызов `service set` уже сам запустил пересборку. Последующий `redeploy` отменил эту сборку (её лог заканчивается строкой `--- Build cancelled: a newer deploy was triggered ---`) и запустил ту же сборку заново с самого начала.

<span id="why-this-can-happen" />

## Почему так происходит

Изменение поля, **влияющего на сборку** — `repoUrl`, `branch`, `sourceType`, `buildCommand`, `dockerfilePath` или `rootDirectory` — немедленно запускает автопересборку работающего сервиса. Сервис, который завершился сбоем или ни разу не был развёрнут, самостоятельно не пересобирается. Изменение поля **только для рантайма** — `startCommand`, `preDeployCommand`, `containerPort`, `watchPatterns` — **не** запускает автопересборку; оно вступает в силу только при следующем деплое.

Легко инстинктивно цеплять `redeploy` после каждого `service set`, но это имеет смысл только для полей только для рантайма.

<span id="possible-solutions" />

## Возможные решения

<span id="check-which-kind-of-field-you-changed" />

### Проверьте, поле какого типа вы изменили

См. [таблицу триггеров пересборки](/concepts/build-pipeline#what-triggers-a-rebuild). Если это поле сборки и сервис работал, пересборка уже запущена — больше ничего делать не нужно. Если сервис завершился сбоем или ни разу не был развёрнут, выполните `lizard redeploy` один раз.

```bash
lizard events   # is a build already running?
```

<span id="only-redeploy-after-runtime-only-changes" />

### Переразвёртывайте только после изменений полей только для рантайма

```bash
lizard service set api --set startCommand="node server.js"
lizard redeploy --service api   # needed here — startCommand doesn't auto-rebuild
```
