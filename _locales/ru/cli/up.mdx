# lizard up

Загружает текущую директорию и выполняет деплой.

<span id="usage" />

## Использование

```bash
lizard up [path] [flags]
```

`up` упаковывает рабочую директорию (или `path`) в tarball, отправляет на узлы сборки и выполняет деплой. Принудительно включает `sourceType=upload` для целевого сервиса, стримит логи сборки через SSE и выводит живой URL по завершении.

Если директория не привязана к проекту, `up` привязывает её к проекту по умолчанию вашего аккаунта (самому старому проекту в вашем личном рабочем пространстве) и деплоит туда — и в TTY, и в CI. Чтобы задеплоить в другое место, сначала выполните `lizard init --name <project>` или передайте `--project`.

<span id="which-service-up-deploys-to" />

### В какой сервис деплоит `up`

1. В сервис, который вы указали через `--service`. Если в проекте нет сервиса с таким именем, `up` создаёт его.
2. В сервис, привязанный к директории.
3. Иначе — в сервис с именем из поля `name` в `package.json` (без scope) или с именем директории. В TTY `up` спрашивает имя и предлагает это.

В последнем случае, если в проекте уже есть сервис с таким именем, `up` деплоит в него. Каждый `up` переключает целевой сервис на источник upload, поэтому сервис из GitHub перестаёт деплоиться при push. Передайте `--service`, чтобы выбрать цель самостоятельно.

<span id="flags" />

## Флаги

| Флаг | Описание |
|------|-------------|
| `-s, --service <name>` | Сервис для деплоя (по умолчанию — привязанный). Если сервиса с таким именем нет, `up` создаёт его |
| `-p, --project <id>` | Имя, slug или ID проекта. В несвязанной директории `up` привязывает её к этому проекту и создаёт проект, если проекта с таким именем нет |
| `--build-command <cmd>` | Переопределить команду сборки |
| `--start-command <cmd>` | Переопределить команду запуска |
| `--pre-deploy-command <cmd>` | Выполняется перед командой запуска при каждом старте контейнера (каждая реплика, каждый перезапуск). Требует команды запуска; сделайте её безопасной для многократного выполнения |
| `--port <number>` | Порт контейнера (`0` = режим воркера). Новые сервисы по умолчанию используют `3000`, если порт не задан через `EXPOSE` в Dockerfile |
| `--region <code>` | Регион для нового сервиса; для существующего игнорируется |
| `-d, --detach` | Запустить деплой и выйти без стриминга логов |
| `-c, --ci` | Только стримить логи сборки и выйти, когда сборка завершится |
| `--no-gitignore` | Загрузить всё, игнорируя `.gitignore` |

<span id="subcommands" />

## Подкоманды

### `lizard up status <app-id>`

Показывает статус сервиса, его URL и статус последней сборки. Передайте ID сервиса, который выводит `up --detach`.

## Примеры

<span id="deploy-the-current-directory" />

### Деплой текущей директории

```bash
lizard up
```

<span id="deploy-to-a-specific-service-with-a-custom-start-command-and-port" />

### Деплой в конкретный сервис с пользовательской командой запуска и портом

Если `api` ещё нет, `up` создаёт его.

```bash
lizard up --service api --start-command "node server.js" --port 8080
```

<span id="deploy-headlessly-in-ci" />

### Безголовый деплой в CI

```bash
export LIZARD_TOKEN=liz_xxx
lizard init --name my-project
lizard up --ci --service api   # creates api on the first run
```

Неудачная сборка или деплой завершается с кодом `1`. С `--ci` код выхода отражает только сборку, поэтому перед тем, как считать релиз завершённым, проверьте `lizard ps --json`. `--detach` завершается с кодом `0`, как только загрузка принята. См. [настройку фреймворка](/framework-guides#prepare-the-project).
