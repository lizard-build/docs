# lizard restart

Постепенный перезапуск текущей сборки — без пересборки.

<span id="usage" />

## Использование

```bash
lizard restart [nameOrId] [flags]
```

<span id="flags" />

## Флаги

| Флаг | Описание |
|------|--------------|
| `-s, --service <name>` | Сервис |
| `--detach` | Вернуться после принятия перезапуска |
| `--wait` | Ждать готовности новой попытки перезапуска; работает с `--json` |
| `--timeout <seconds>` | Бюджет ожидания готовности с `--wait`; по умолчанию `120` |
| `--json` | Вернуть JSON для скриптов |

<span id="examples" />

## Примеры

<span id="restart-a-service" />

### Перезапустить сервис

```bash
lizard restart --service api
```

<span id="restart-without-streaming-logs" />

### Перезапуск без потоковой передачи логов

```bash
lizard restart --service api --detach
```

<span id="wait-before-running-the-next-check" />

### Подождать перед запуском следующей проверки

Требуется CLI 0.3.94 или новее. Используйте 0.3.95 или новее для рабочих процессов без HTTP.

```bash
lizard --json restart --service api --wait --timeout 120
```

Без `--wait` JSON-режим возвращается после принятия перезапуска. С `--wait` результат включает `ok`, `status`, `attemptId` и `waitedMs`. CLI ждёт новую попытку перезапуска, поэтому неизменный статус от до запроса не считается успехом. Неудачное ожидание или таймаут возвращают ненулевой код выхода.

Для HTTP-сервисов CLI также проверяет домен сервиса дважды. Рабочие процессы с `containerPort=0` используют статус готовности из бэкенда и не требуют HTTP-слушателя, даже когда у них есть сгенерированный домен.

```bash
lizard --json restart --service worker --wait --timeout 60
```

Таймаут применяется к ожиданию готовности после запроса на перезапуск. Он не отменяет перезапуск, а сетевые вызовы могут сделать общее время выполнения команды дольше. Проверьте данные приложения или эндпоинт здоровья после команды, когда вашему рабочему процессу требуется больше, чем готовность процесса.
