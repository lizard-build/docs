# Переменные и секреты

Lizard хранит конфигурацию как **секреты**. У них есть два уровня видимости — **сервис** (по умолчанию) и **проект** (`--global`) — и они объединяются в окружение приложения в строго заданном порядке приоритета. Глобального уровня рабочего пространства нет.

<span id="setting-variables" />

## Установка переменных

`lizard secrets set` принимает переменное число аргументов — можно задать один или несколько секретов сразу. По умолчанию он пишет в **привязанный сервис**:

```bash
lizard secrets set DATABASE_URL=postgres://… LOG_LEVEL=info
lizard secrets set API_KEY=sk_live_… --service api
```

Добавьте `--global`, чтобы записать в **область проекта** (увидит каждый сервис в проекте):

```bash
lizard secrets set NODE_ENV=production --global
```

<span id="listing-deleting-importing" />

## Просмотр, удаление, импорт

```bash
lizard secrets list                       # current scope
lizard secrets list --show                # reveal values
lizard secrets delete OLD_KEY ANOTHER_KEY # variadic; add -y in scripts
cat .env | lizard secrets import          # KEY=value lines from stdin
```

`secrets import` читает простые строки `KEY=value` и сохраняет кавычки как часть значения. `secrets delete` запрашивает подтверждение; передайте `-y`, если команда запускается вне терминала.

Все флаги описаны в [справке по команде `lizard secrets`](/cli/secrets).

<span id="scoping" />

## Область видимости

| Уровень | Команда | Хранится как | Видимость для |
|---------|---------|--------------|-----------|
| **Сервис** (по умолчанию) | `lizard secrets set K=v --service <svc>` | `secrets.services[<svc>]` | только этот сервис |
| **Проект** (глобальный) | `lizard secrets set K=v --global` | `secrets.shared` | все сервисы в проекте |

**По умолчанию — уровень сервиса.** Скомпрометированный сервис может прочитать своё окружение — более широкая область видимости означает больше учётных данных без нужды. Используйте `--global` только для несекретных, заведомо публичных значений вроде `LOG_LEVEL`, `NODE_ENV`, флагов функций или публичного URL фронтенда `SENTRY_DSN`. Если не уверены, является ли значение секретом — считайте его секретом и ограничьте сервисом.

`DATABASE_URL` и `REDIS_URL` каждого запущенного аддона Postgres и Redis уже попадают во все сервисы проекта с самым низким приоритетом. Чтобы выбрать конкретный аддон или использовать его приватный URL, привяжите его к каждому потребителю через [ссылку](/variables/references), а не через `--global`:

```bash
lizard secrets set DATABASE_URL='${{postgres.DATABASE_PRIVATE_URL}}' --service api
lizard secrets set DATABASE_URL='${{postgres.DATABASE_PRIVATE_URL}}' --service worker
```

Если значения аддона изменятся, каждый потребитель получит новое значение при следующем деплое или изменении переменных.

<span id="precedence" />

## Приоритет

Когда один ключ задан в нескольких местах, **побеждает последний записавший**:

```
addon-issued env  <  project secrets  <  project env  <  app env  <  app secrets  <  platform vars
```

Поэтому **секреты приложения перекрывают секреты проекта**, а **платформенные переменные** (`PORT`, `LIZARD_SERVICE_NAME`, `LIZARD_PROJECT_ID`, `LIZARD_PUBLIC_DOMAIN`, `LIZARD_PRIVATE_DOMAIN`) применяются в самом конце и их нельзя переопределить. `PORT` задаётся только тогда, когда у сервиса есть HTTP-порт. Если задать `PORT` самостоятельно, порт, на который Lizard направляет трафик, изменится при следующем деплое, если только порт не был задан через `lizard port`.

<span id="build-time-vs-runtime" />

## Время сборки и время выполнения

Большинство изменений переменных вступают в силу **без пересборки** — сервис перезапускается и подхватывает их за несколько секунд. Исключения — значения времени сборки, зашиваемые в образ:

- Изменение значения `VITE_*` или `NEXT_PUBLIC_*` сразу запускает пересборку затронутых запущенных сервисов (для `--global` — всех запущенных сервисов).
- Lizard зашивает эти значения в виде строк `ENV` для сервисов из GitHub (Dockerfile, который генерирует lizardpack, или Dockerfile в корне репозитория) и для Node-сервисов, собираемых через `buildCommand` / `startCommand`. Сервис с собственным `dockerfilePath` или загруженный через `lizard up` без этих команд не получает переменные Lizard во время сборки; build args не получает ни один сервис, кроме `COMMIT_SHA`. Для публичных значений в таких случаях закоммитьте их в `.env.production`, задайте команду сборки или впишите их в свой Dockerfile.

См. [Пайплайн сборки → триггеры пересборки](/concepts/build-pipeline#what-triggers-a-rebuild).

<span id="verifying" />

## Проверка

Доступ к сервисам по shell (`lizard ssh`) отключён, поэтому проверяйте значения другим способом:

```bash
lizard logs --build --service api          # warns about every empty ${{…}} reference
lizard secrets list --service api --show   # stored values
lizard secrets list --service api --ref    # reference templates you can use
```

Если ожидаемого значения нет, см. [Устранение неполадок → секрет или ссылка не отображается](/variables/troubleshooting/reference-not-applied).

<span id="local-development" />

## Локальная разработка

Запустите команду **локально** с внедрёнными секретами проекта и сервиса:

```bash
lizard run --service api -- node scripts/seed.js
```

Значения передаются как сохранены: ссылки `${{…}}` остаются буквальным текстом, а платформенные переменные (`PORT`, `LIZARD_*`) не внедряются. Если скрипту нужна база данных, запустите его с реальными параметрами подключения аддона:

```bash
lizard run --service postgres -- node scripts/seed.js
```

См. [что внедряет `lizard run`](/cli/run#what-run-injects).
