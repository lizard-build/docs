# Перекрёстные ссылки

Ссылки позволяют сервису читать значения другого сервиса или аддона без копирования учётных данных. Они хранят каждое значение в одном месте; потребители подхватывают изменения при следующем деплое.

<span id="syntax" />

## Синтаксис

```
${{<name>.<KEY>}}
```

- `<name>` — имя целевого сервиса или аддона (то, что показано в дашборде и используется в `lizard add -n`).
- `<KEY>` — ключ, который отдаёт цель. Аддон отдаёт свои параметры подключения. Сервис отдаёт свои переменные и секреты уровня проекта и сервиса, а также значения `LIZARD_*` и `PORT`. `DATABASE_URL` и `REDIS_URL`, которые Lizard подставляет в сервис из аддонов, сервис не отдаёт; для них ссылайтесь на аддон.

Используйте их везде, где принимается значение — чаще всего в секрете:

```bash
lizard secrets set DATABASE_URL='${{postgres.DATABASE_URL}}' --service api
```

<span id="how-they-resolve" />

## Как они разрешаются

- Ссылки разрешаются **во время деплоя** по значениям, которые отдаёт цель.
- Ссылки, заданные в секрете (`lizard secrets set` или дашборд), сопоставляются с **текущим именем** цели. Переименование цели ломает их; после переименования обновите каждую `${{oldname.KEY}}`. Ссылки, заданные при создании через `lizard add -v`, следуют за целью при переименовании.
- Ссылка на **отсутствующую** цель или ключ разрешается в **пустую строку** — она *не* проваливает деплой. В логе сборки для каждой пустой ссылки выводится предупреждение с указанием причины.
- Ошибку выдают только **циклические** ссылки.

> После настройки ссылки проверьте в логе сборки, нет ли пустых:
> ```bash
> lizard logs --build --service api
> ```

Если ссылка не отображается так, как ожидалось, см. [Устранение неполадок → секрет или ссылка не отображается](/variables/troubleshooting/reference-not-applied).

<span id="common-patterns" />

## Типичные сценарии

**Подключить аддон к нескольким сервисам** — привяжите на каждом потребителе; внутри проекта используйте приватный URL:

```bash
lizard secrets set REDIS_URL='${{redis.REDIS_PRIVATE_URL}}' --service api
lizard secrets set REDIS_URL='${{redis.REDIS_PRIVATE_URL}}' --service worker
```

**Ссылаться на значение другого сервиса** — например, делиться вычисленным URL или токеном. `LIZARD_PUBLIC_DOMAIN` — это просто имя хоста, и он существует, когда у сервиса есть домен; `LIZARD_PRIVATE_DOMAIN` (`<name>.lizard.internal`) обеспечивает доступ к сервису внутри проекта:

```bash
lizard secrets set UPSTREAM_URL='https://${{api.LIZARD_PUBLIC_DOMAIN}}' --service web
lizard secrets set INTERNAL_API='http://${{api.LIZARD_PRIVATE_DOMAIN}}:8080' --service web
```

**Ссылаться на второй аддон того же типа** — используйте его сгенерированное имя:

```bash
lizard secrets set CACHE_URL='${{redis-winter-otter.REDIS_URL}}' --service api
```

<span id="why-not-just-use---global" />

## Почему не просто `--global`?

Размещение общего значения в области проекта (`--global`) раскрывает его для *каждого* сервиса, включая те, которые ему не нужны. Ссылка хранит значение в одном месте и привязывает его только там, где вы её задали. Учтите, что каждый сервис и так получает один `DATABASE_URL` и один `REDIS_URL` от аддонов Postgres и Redis проекта с самым низким приоритетом; если аддонов одного типа несколько, какой из них попадёт в сервис, не определено. Ссылка их переопределяет. См. [Область видимости секретов](/variables#scoping).
