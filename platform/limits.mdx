# Limits

On Lizard, an app runs up to 5 replicas per service after the first paid Pro invoice, and 1 during the trial. Sandbox limits count vCPU, not sandboxes: Pro runs up to 40 vCPU of sandboxes at once, Pro 5x 220 and Pro 20x 1,200. Pro, Pro 5x and Pro 20x have no limit on sandbox starts. The trial runs 1 Small and 2 Mini sandboxes at a time, only in US regions, and deletes each sandbox 1 hour after it starts at the latest. Sandbox sizes run from Mini (1 vCPU / 2 GB) to Large (8 vCPU / 16 GB), and sandbox egress is included up to 2 TB per account over a rolling 30 days. A workspace owner can also set [workspace limits](#workspace-limits) for one workspace. Limits depend on the resource, plan, and account: a per-replica setting is not the total available to a service or an account. Check your plan and the result of the create or scale request before choosing resources.

## Applications

| Setting | Scope | What to check |
|---|---|---|
| CPU and memory | Each replica | Three replicas with a 2 vCPU / 2 GiB ceiling have a combined configured ceiling of 6 vCPU / 6 GiB. This is not a usage forecast. |
| Replica count | Service and plan | Your plan sets the limit: 1 per app during the Pro trial, 5 on every paid plan after the first paid invoice and on Enterprise. The API accepts at most 10, which only an account override can reach. |
| Account resource cap | Account owner | A second project does not necessarily create a second quota. Ask for the effective account cap before planning a large deployment. |
| Worker mode | Service | `containerPort=0` runs without an HTTP listener or public load-balancer route. |
| Custom domain | Hostname | Wildcard custom domains are not accepted. Use a specific hostname and complete ownership and DNS checks. |

## Sandboxes

[Sandboxes](/sandboxes) run commands and agent tasks in Firecracker microVMs; see [runtime and isolation](/sandboxes#runtime-and-templates). The limits below apply to every sandbox an account runs.

<span id="sandbox-sizes" />

### Sizes

| Size | CPU and memory | Disk | Price while running |
|---|---|---|---|
| Mini | 1 vCPU / 2 GB | 5 GB | $0.0081 per hour |
| Small | 2 vCPU / 4 GB | 20 GB | $0.0162 per hour |
| Medium (default outside the trial) | 4 vCPU / 8 GB | 40 GB | $0.0324 per hour |
| Large | 8 vCPU / 16 GB | 80 GB | $0.0648 per hour |

CPU, memory and disk are included in the price while the sandbox runs. A paused sandbox and each snapshot cost $0.14 per GB-month of used disk space; see [storage and billing](/sandboxes#storage-and-billing). Persistent Volumes bill separately. Mini starts only from the `base`, `claude`, `codex` and `interpreter` templates, without a Persistent Volume; otherwise create returns HTTP 400 with `code` set to `SANDBOX_SIZE_NOT_ALLOWED`. During the trial, Small is the default size, an account runs 1 Small and 2 Mini at a time, Medium and Large unlock after the first paid invoice, sandboxes run only in US regions, and each sandbox is deleted 1 hour after it starts at the latest; see [Billing](/platform/billing#trial).

<span id="sandbox-account-limits" />

### Account limits

These limits cap how much sandbox vCPU an account runs at once, the largest sandbox it can run and how fast it starts new ones. They follow the account owner's plan. Trial limits apply until the first paid invoice; see [Billing](/platform/billing#limits).

| Plan | vCPU at once | Largest size | Starts per minute | Per hour | Per day |
|---|---|---|---|---|---|
| Pro trial | 1 Small + 2 Mini at a time | Small | 6 | 30 | 100 |
| Pro | 40 | Large | Unlimited | Unlimited | Unlimited |
| Pro 5x | 220 | Large | Unlimited | Unlimited | Unlimited |
| Pro 20x | 1,200 | Large | Unlimited | Unlimited | Unlimited |
| Enterprise | Per workspace, set by your agreement | Large | 120 per user | No limit | No limit |

During the trial, you can start 50 Small and 100 Mini sandboxes in total across all your workspaces. Creates and forks count, including deleted sandboxes; resumes do not. After a size reaches its allowance, new starts of that size return `TRIAL_STARTS_USED` until you start Pro.

A sandbox uses the vCPU of its size: Mini 1, Small 2, Medium 4, Large 8. On the paid plans, a new sandbox fits when the vCPU already running plus its own vCPU is at or below your limit. Mix sizes as you like. This table shows how many sandboxes of one size fit at once:

| Plan | Mini | Small | Medium | Large |
|---|---|---|---|---|
| Pro trial | 2 | 1 | Not available | Not available |
| Pro | 40 | 20 | 10 | 5 |
| Pro 5x | 220 | 110 | 55 | 27 |
| Pro 20x | 1,200 | 600 | 300 | 150 |

On Pro, 3 Large and 6 Small sandboxes use 36 of 40 vCPU, so one more Medium fits but another Large does not.

- Lizard counts limits per account owner, across all of the owner's workspaces. A second workspace does not add a second allowance.
- On the trial and the paid plans, running means running or resuming. A paused sandbox uses no vCPU; resuming one needs room for its vCPU.
- A start is a new sandbox. A resume is not a start. A create that fails on Lizard's side does not count.
- Over a limit, create and resume return HTTP 429 with `code` set to `SANDBOX_LIMIT_REACHED` (vCPU at once) or `SANDBOX_RATE_LIMITED` (starts). A start-rate refusal includes a `Retry-After` header.
- During the trial, a second Small or a third Mini running at once, whether you create, fork or resume it, returns HTTP 403 with `code` set to `TRIAL_SIZE_RUNNING`; the body has `size`, `sizeLimit`, `allowedSizes` and `sizeLimits`. Pause or delete one, or, for Small, start a Mini. A Medium sandbox returns HTTP 403 with `TRIAL_SANDBOX_SIZE` (`allowedSizes` is `["small", "mini"]`), a Large one returns HTTP 403 with `SANDBOX_SIZE_NOT_ALLOWED`, and a region outside the US returns HTTP 403 with `TRIAL_SANDBOX_REGION`.
- During the trial, a create or fork with a lifetime over 1 hour returns HTTP 403 with `code` set to `TRIAL_SANDBOX_LIFETIME` and `maxTimeoutMs: 3600000`; see [Lifetime](#sandbox-lifetime).
- `GET /api/sandboxes/limits` returns your limits and what is running now, with `running` (sandboxes) and `runningVcpu`. During the trial it also returns `sizeLimits` (`{"small": 1, "mini": 2}`) and `runningBySize`.
- Enterprise has no fixed limit on sandboxes running at once. Each customer's agreement sets the limit per workspace. Running, paused and crashed sandboxes all count toward it. Over it, create and fork return HTTP 429 with `code` set to `SANDBOX_LIMIT_REACHED`. One user can create up to 120 sandboxes a minute in each region.
- The dashboard shows the vCPU in use and your vCPU limit next to **New Sandbox**. For more than 1,200 vCPU at once, contact us about Enterprise.

A `SANDBOX_LIMIT_REACHED` refusal says how much you run and how much the new sandbox needs. `unit` is `vcpu`, `limit` and `running` are in vCPU, and `needed` is the vCPU of the sandbox you asked for:

```json
{
  "error": "Your plan runs up to 40 vCPU of Sandboxes at once. 38 are in use and this sandbox needs 4. Stop or pause a sandbox, or move to a higher Pro tier.",
  "code": "SANDBOX_LIMIT_REACHED",
  "tier": "pro",
  "unit": "vcpu",
  "limit": 40,
  "running": 38,
  "needed": 4
}
```

A `SANDBOX_SIZE_NOT_ALLOWED` refusal names your limit tier and, in vCPU, the largest sandbox it allows:

```json
{
  "error": "Large Sandboxes start after your first Pro payment. Start Pro now in Billing to use them.",
  "message": "Large Sandboxes start after your first Pro payment. Start Pro now in Billing to use them.",
  "code": "SANDBOX_SIZE_NOT_ALLOWED",
  "tier": "trial",
  "maxSandboxCpus": 4
}
```

To run more, stop or pause a sandbox, use a smaller size, or move to a bigger plan; see [changing plans](/platform/billing#changing-plans).

<span id="sandbox-egress" />

### Network egress

Sandbox egress has no separate per-GB charge. The included allowance is 2 TB per account over a rolling 30 days, shared across the account's sandboxes. If your workload needs more, contact us before running it.

<span id="sandbox-lifetime" />

### Lifetime

| Setting | Current create API |
|---|---|
| Templates | `base`, `interpreter`, `codex`, `desktop`, `opencode`, `pi`, `prime`, `claude`; `desktop-camoufox` in US East only |
| Raw API default lifetime | `timeoutMs: 0`, no expiration |
| Lizard SDK default lifetime | 300000 ms, five minutes |
| Explicit lifetime range | Integer milliseconds from 0 to 2147483647 |
| Updating a lifetime | At least 1000 ms; it is not an idle timer |
| Trial lifetime | At most 1 hour (3600000 ms) after the sandbox starts; no lifetime gets 1 hour |
| Persistent volume attachment | One sandbox at a time, on the volume's node |

The CLI also defaults to five minutes; the dashboard defaults to no expiration. Commands do not reset the deadline. For pause, snapshots, fork and what each one keeps, see the sandbox [lifecycle](/sandboxes#lifecycle).

During the trial, every sandbox is deleted 1 hour after it starts at the latest. A create or fork that sets no lifetime (`timeoutMs` `0`, absent, or Never) gets 1 hour; a longer lifetime returns HTTP 403 with `code` set to `TRIAL_SANDBOX_LIFETIME` and `maxTimeoutMs: 3600000`. `POST /api/sandboxes/{id}/timeout` cannot move a trial sandbox's deadline past 1 hour after it was created; that 403 also has `latestExpiresAt`. Sandboxes created before 2026-11-10 keep no expiration. Longer lifetimes unlock after the first paid invoice.

## Workspace limits

A workspace owner can cap one workspace, for example one that a customer reaches with a scoped API key. These caps apply on top of the account limits above, to everyone who works in the workspace.

| Limit | What counts | Flag |
|---|---|---|
| Sandboxes | Sandboxes running or resuming at once; paused ones don't count | `--sandboxes <n>` |
| CPU | vCPU the workspace's apps and databases use now, as measured | `--cpu <vcpus>` |
| Memory | Memory the workspace's apps and databases use now, as measured | `--memory <size>` |
| Disk | Data written to the workspace's databases and volumes | `--disk <size>` |

Only the owner sets them, with [`lizard workspace limits`](/cli/workspace#lizard-workspace-limits-name-or-id), signed in with the browser or an API key with no scopes. Any member, and any key that reaches the workspace, can read them with the current use.

- At the sandbox cap, create, fork and resume return HTTP 429 with `code` set to `WORKSPACE_SANDBOX_LIMIT`.
- While apps and databases use as much CPU or memory as allowed, deploy, redeploy, restart, scale up, new databases and resuming a paused app or database return HTTP 429 with `code` set to `WORKSPACE_USAGE_LIMIT`. Running services keep running.
- While data fills the disk cap, new volumes, volume growth, new databases and template deploys return the same `WORKSPACE_USAGE_LIMIT`. Data already written stays.
- A sandbox's own disk does not count toward the disk cap.

## Regions

The current configured regions include US East (Virginia), `us-east-1`, and EU West (Limburg), `eu-west-lim-a`. A region in the catalog does not guarantee available capacity for every resource. Check region choices when creating the resource; a sandbox using an existing volume must run on that volume's node. [`lizard regions`](/cli/regions) lists the regions open to your account; see [regions](/deploy/regions).

## Before increasing scale

Check the active plan, per-replica settings, account cap, workspace limits, database connection limit, and storage growth together. Use [scaling](/deploy/scaling), [metrics](/observability/metrics), and [pricing](https://lizard.build/pricing) to compare configured capacity with measured usage. Rates for every resource are on the [billing page](/platform/billing#resource-rates).
