# Limits

Limits depend on the resource, plan, and account. A per-replica setting is not the total available to a service or an account. Check your current plan and the result of the create or scale request before sizing a workload.

## Applications

| Setting | Scope | What to check |
|---|---|---|
| CPU and memory | Each replica | Three replicas with a 2 vCPU / 2 GiB ceiling have a combined configured ceiling of 6 vCPU / 6 GiB. This is not a usage forecast. |
| Replica count | Service and plan | The API accepts 1–10; plan limits can reduce that range. Standard plan checks allow 1, or 5 for Pro/Enterprise, with account overrides. |
| Account resource cap | Account owner | A second project does not necessarily create a second quota. Ask for the effective account cap before planning a large deployment. |
| Worker mode | Service | `containerPort=0` runs without an HTTP listener or public load-balancer route. |
| Custom domain | Hostname | Wildcard custom domains are not accepted. Use a specific hostname and complete ownership and DNS checks. |

Sandboxes run short-lived commands and agent tasks in Kubernetes pods with the runc runtime. They share the host kernel; they are not Firecracker virtual machines. Restrict credentials and network access when running code you do not trust.

<span id="sandbox-account-limits" />

### Account limits

These limits cap how many sandboxes an account runs at once and how fast it starts new ones. There is no plan to choose: they rise automatically with what the account owner has paid in total (credit purchases and auto top-ups).

| Account | Running at once | Starts per minute | Per hour | Per day |
|---|---|---|---|---|
| Free trial: card saved, nothing paid yet | 5 | 6 | 30 | 100 |
| After a first top-up of any amount | 20 | 12 | 60 | 200 |
| $20 paid in total | 100 | 24 | 120 | 400 |
| Enterprise | Custom | Custom | Custom | Custom |

- Limits are counted per account owner, across all of the owner's workspaces. A second workspace does not add a second allowance.
- Running means running or resuming. A paused sandbox does not count; resuming one needs a free slot.
- A start is a new sandbox. A resume is not a start. A create that fails on Lizard's side does not count.
- Over a limit, create and resume return HTTP 429 with `code` set to `SANDBOX_LIMIT_REACHED` (running) or `SANDBOX_RATE_LIMITED` (starts). A start-rate refusal includes a `Retry-After` header.
- The dashboard shows how many sandboxes are running against your limit next to **New Sandbox**. For more than 100 at once, contact us about Enterprise.

<span id="sandbox-egress" />

### Network egress

Sandbox egress is included up to 2 TB per account over a rolling 30 days, counted across all of the account's sandboxes. Past that, the account's sandboxes lose outbound network until the 30-day total falls back under 2 TB. Nothing extra is charged.

<span id="sandbox-lifetime" />

### Lifetime

| Setting | Current create API |
|---|---|
| Templates | `base`, `codex`, `interpreter` |
| Raw API default lifetime | `timeoutMs: 0`, no expiration |
| Lizard SDK default lifetime | 300000 ms, five minutes |
| Explicit lifetime range | Integer milliseconds from 0 to 2147483647 |
| Updating a lifetime | At least 1000 ms; it is not an idle timer |
| Persistent volume attachment | One sandbox at a time, on the volume's node |

The SDK and CLI default to a five-minute lifetime. The raw API and dashboard default to no expiration. Set an explicit lifetime: `timeoutMs: 0` at creation disables expiration; a positive value sets a deadline. `setTimeout` accepts 1000–2147483647 ms, not zero. Commands do not reset the deadline. This is not an idle timer.

Create a sandbox, run commands, then call `kill`. `connect` attaches to an existing sandbox; it does not resume a stopped one. Pause and resume are available. Fork, snapshot, restore, and file watching currently return HTTP 501. SSH access is not available for the current runtime.

## Regions

The current configured regions include US East (Virginia), `us-east-1`, and EU West (Limburg), `eu-west-lim-a`. A region in the catalog does not guarantee available capacity for every resource. Check region choices when creating the resource; a sandbox using an existing volume must run on that volume's node.

## Before increasing scale

Check the active plan, per-replica settings, account cap, database connection limit, and storage growth together. Use [scaling](/deploy/scaling), [metrics](/observability/metrics), and [pricing](https://lizard.build/pricing) to compare configured capacity with measured usage.
