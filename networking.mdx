# Networking

Every service gets a generated `*.onlizard.com` domain with automatic TLS the moment it deploys, regardless of region. Attach your own hostname when you're ready to go live.

## Generated domains

A service's default domain is created for you, in the form `<name>-<suffix>.onlizard.com`. Older services keep `<words>.<region>.onlizard.com`. Show it:

```bash
lizard domain                    # show the service's current domain
lizard domain generate           # claim a *.onlizard.com subdomain if the service has none
```

`lizard domain generate` returns the existing generated domain when there is one, and fails while the service has a custom domain. Files served from [Managed Object Storage](/addons/storage) use a gateway host instead: `s3-eu-west-1.onlizard.com` or `s3-us-east-1.onlizard.com`.

## Attach a custom domain

The hostname is a **positional argument** — there is no `add` subcommand:

```bash
lizard domain app.example.com --service web
```

Lizard returns the DNS records to create (a `CNAME` for the hostname and a `TXT` record for verification). Add them at your DNS provider.

## Verify

Once DNS has propagated, activate the domain:

```bash
lizard domain verify app.example.com --service web
```

This checks the `TXT` record and activates the domain. TLS is provisioned automatically.

## Remove a domain

```bash
lizard domain delete app.example.com --service web
lizard domain rm app.example.com --service web --yes   # alias, skip confirmation
```

## Change the port your service listens on

Domains route to the service's container port. If your service listens on another port, change the container port and redeploy:

```bash
lizard port 8080 --service web
lizard redeploy --service web
```

## Worker services

A [worker-mode service](/deploy/workers) (`containerPort=0`) may still show a generated domain, but it serves nothing — there's no listener and no load-balancer route. Don't attach a custom domain to a worker.

## Private networking

Services in the same project reach each other at `<service>.lizard.internal`, on any port the service listens on, without a public domain. Reference the hostname as `${{api.LIZARD_PRIVATE_DOMAIN}}`. Managed Postgres and Managed Redis expose `DATABASE_PRIVATE_URL` and `REDIS_PRIVATE_URL` on the same network. These names resolve only inside the project.

```bash
lizard secrets set API_URL='http://${{api.LIZARD_PRIVATE_DOMAIN}}:8080' --service web
```

## Manage in the dashboard

Open a service in the dashboard (`lizard open`) and go to **Settings → Networking**. It shows each domain's verification and DNS status and lets you add or remove hostnames.
