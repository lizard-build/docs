# A secret or reference isn't showing up in my service

You set a secret or a `${{name.KEY}}` reference, redeployed, and the running service still doesn't see the value you expect.

## What this means

The value you set never made it into the service's merged environment — or something else in the merge overwrote it before the app started.

## Why this can happen

- **The reference target or key doesn't exist.** A reference to a missing service/addon name, or a key that addon doesn't expose, resolves to an **empty string** instead of failing the deploy. The build log prints a warning for each empty reference with the reason; a variable change applied by restart, with no build, shows no warning. A renamed target counts as missing: references match the current name.
- **Something with higher precedence overrode it.** Values merge in a fixed order — `addon-issued env < project secrets < project env < app env < app secrets < platform vars` — so a project-scoped (`--global`) secret can be silently shadowed by a service-scoped one with the same key, and platform variables (`PORT`, `LIZARD_SERVICE_NAME`, `LIZARD_PROJECT_ID`, `LIZARD_PUBLIC_DOMAIN`, `LIZARD_PRIVATE_DOMAIN`) always win. Setting `PORT` yourself changes the port Lizard routes to instead, unless the port was set with `lizard port`.
- **A build-time value didn't reach the build.** Most variable changes apply with no rebuild — the service restarts to pick them up. `VITE_*` and `NEXT_PUBLIC_*` values are baked into the built assets, and changing one starts a rebuild of running services right away. A service that was crashed or stopped at the time is skipped, and a service with a custom `dockerfilePath` or uploaded with `lizard up` without build/start commands never gets these values at build time.

## Possible solutions

### Check the build log for empty references

Shell access to services (`lizard ssh`) is turned off. The build log is the place to look: each empty reference gets a line like `==> Warning: ... is empty` with the reason.

```bash
lizard logs --build --service api
```

Then list the reference templates that are valid in this scope, and compare the name and key with yours. Check keys against the addon's [documented variables](/addons):

```bash
lizard secrets list --service api --ref
```

### Check for a scope collision

List secrets in both scopes and compare:

```bash
lizard secrets list --service api --show
lizard secrets list --global --show
```

Remember **app secrets override project secrets** — if a service-scoped value exists for the same key, it wins over anything set with `--global`.

### Rebuild after a build-time change

If the changed key is `VITE_*` or `NEXT_PUBLIC_*` and the service was crashed or stopped when you changed it, trigger a rebuild:

```bash
lizard redeploy --service api
```

See [Build-time vs. runtime](/variables#build-time-vs-runtime) and [Build Pipeline → what triggers a rebuild](/concepts/build-pipeline#what-triggers-a-rebuild).
